# OLP Static Code Audit Report

Target: `olp-main(11)(2).zip`  
Scope reviewed: Rust backend, storage layer, provider transport layer, Svelte console, SQL migrations, deployment scripts, and CI scripts  
Size: approximately **111,153 Rust LOC + 26,046 Svelte/TypeScript LOC**

## Conclusion

Even after excluding forced nitpicks and findings that could not be adequately supported, the audit identified **32 meaningful issues**.

| Severity | Count | Meaning |
|---|---:|---|
| High | 5 | Quota bypass, connection contract violations, incorrect cost calculation, upstream amplification, or serious operational outage risk |
| Medium | 20 | Sticky quota after transient failures, incorrect billing/session state, duplicate execution, N+1 queries, or scalability problems |
| Low | 7 | API inconsistency, UX/auditability problems, long-term compatibility risks, or explicit performance debt |

The first five issues that should be fixed are:

1. **The TPM hard limit can actually be bypassed**
2. **The five-minute connection-age policy forcibly terminates valid long-running streams**
3. **Pricing revision selection permanently prefers stale provider-specific overrides**
4. **One video-list request can generate up to 100 upstream requests and database updates**
5. **Maintenance combines large deletions and rollups into one unbounded transaction**

The repository is generally careful about security boundaries and data modeling. In particular, the egress SSRF defenses, durable request-metadata delivery, ambiguous-retry prevention for media side effects, and SQLx boundary checks are well designed.

The main problem is that several critical contract violations are hidden behind otherwise sophisticated surrounding code. Quota enforcement is called “hard” even though usage beyond the reservation is not debited. Route timeouts can be configured for tens of days while the transport forcibly closes connections after roughly five minutes. Pricing revisions are modeled as immutable, but the lookup SQL sorts provider specificity before revision freshness.

# Detailed Findings

## 1. [High] The TPM “hard limit” can be bypassed through under-reservation

**Evidence**

- `apps/olp/src/request_admission/limits.rs:338-386`
- `apps/olp/src/gateway/limits.rs:19-58,104-183`
- `crates/storage/src/limits.rs:96-120`
- `crates/storage/scripts/reconcile_limits.lua:1-20`
- `crates/storage/tests/integration/distributed_limits_valkey.rs:369-408`

Input-token reservation is initially approximated using roughly `body bytes / 4`, and later in the canonical stage using `text.chars().count() / 4`.

When actual usage is smaller than the reservation, the difference is refunded. However, when actual usage exceeds the reservation, the excess is not additionally debited.

The existing test for `reserved=4`, `actual=7` explicitly preserves final usage as 4. This is therefore not merely an accidental omission; it is part of the current behavioral contract.

**Impact**

- Unicode-heavy or structurally dense input can consume substantially more real tokens than the reservation.
- Upstream cost and model load can exceed the configured limit while the Valkey counter records only the underestimated amount.
- If the product or API describes this as a hard TPM limit, this violates the security and cost-isolation contract.

**Fix**

- For a real hard limit, reserve a tokenizer-specific safe upper bound and refund the difference afterward.
- Alternatively, atomically debit excess usage when actual usage exceeds the reservation. If the extra debit pushes the account over the limit, record quota debt and block subsequent requests.
- If neither is feasible, rename and document the feature as `estimated admission TPM` rather than a hard limit.

## 2. [Medium] Invalid requests that never reach upstream still consume TPM reservations

**Evidence**

- `apps/olp/src/request_admission.rs:439-475,478-545,679-682`
- `apps/olp/src/request_admission/limits.rs:95-113`

The system reserves JSON body tokens before validating JSON depth. On paths such as excessively deep JSON, malformed multipart boundaries, or pre-authorization failure, it releases the concurrency lease but does not reconcile the token reservation with `actual=0`.

**Impact**

An attacker or malfunctioning client that possesses a shared API key can exhaust the current minute’s TPM budget without issuing any upstream request. From the user’s perspective, failed requests silently destroy available quota.

**Fix**

Replace the scattered cleanup logic with an RAII state machine that performs `actual=0` reconciliation and concurrency release unless accounting is explicitly completed successfully.

Token and concurrency leases should be represented as separate resources with independent state transitions.

## 3. [Medium] Failures and cancellations without usage data retain the full estimated output reservation

**Evidence**

- `apps/olp/src/gateway/telemetry.rs:118-149,251-263,389-392`
- `apps/olp/src/gateway/limits.rs:199-221`

Reconciliation only occurs when actual token usage is `Some`. If the provider returns a 5xx response, a protocol error occurs, the first-byte timeout fires, or the client cancels before usage is available, the full input-plus-default-output estimate remains charged to the current minute.

**Impact**

A small number of failed requests during a provider outage can exhaust TPM. Even after the provider recovers, valid traffic can remain rejected until the minute boundary.

The distortion is especially large when the default output estimate is 4096 tokens.

**Fix**

- Separate input and output reservations.
- For failures before upstream transmission, reconcile to `actual=0`.
- After upstream transmission but without final usage, retain only a conservative input estimate and refund the output reservation.
- Record unresolved or ambiguous accounting in a dedicated metric.

## 4. [Medium] Quota cleanup uses a single 250 ms attempt, turning transient Valkey latency into sticky quota

**Evidence**

- `apps/olp/src/request_admission/limits.rs:45-54,71-92`
- `apps/olp/src/gateway/limits.rs:199-221`

Release and reconciliation cleanup operations receive a 250 ms timeout and are attempted only once. There is no retry queue or durable cleanup outbox.

**Impact**

- A concurrency slot can remain occupied until its lease TTL expires.
- A token refund can be permanently lost from the current minute bucket.
- Valkey tail latency is amplified into a tenant-level quota outage, independently of whether request processing itself succeeded.

**Fix**

Add idempotent cleanup operations and a bounded retry worker. However, the non-idempotent reconciliation problem in finding 5 must be fixed first.

## 5. [Medium, Design Fragility] Token reconciliation is not idempotent, preventing safe retries

**Evidence**

- `crates/storage/src/limits.rs:96-120,215`
- `crates/storage/scripts/reconcile_limits.lua:6-20`

The reconciliation script decreases the counter without a lease identity or an “already reconciled” state. Running the same refund twice decreases the counter twice. `LimitLease` is also cloneable.

This does not prove that the current implementation always double-refunds. The problem is structural: adding reliable cleanup retries would immediately create a quota-bypass risk.

**Fix**

Assign each token reservation a lease ID and make reconciliation an atomic Valkey state transition:

```text
pending -> reconciled
```

The state transition and counter update should happen in the same Lua script. A second reconciliation for the same lease must be a no-op.

## 6. [High] The transport’s five-minute connection age forcibly terminates valid long-running streams

**Evidence**

- `apps/olp/src/listener.rs:40-41,301-342`
- `crates/storage/src/configuration/route_lifecycle.rs:68-75`
- `crates/storage/src/configuration/validation.rs:100-126`
- `crates/domain/src/routing.rs:237-268`

A TCP connection begins graceful shutdown five minutes after acceptance and is force-closed 30 seconds later.

Meanwhile, a route’s `overall_timeout_ms` can be configured up to `i32::MAX`, which is approximately **24.85 days**.

For HTTP/2, a new stream opened on a connection that is already 4 minutes and 59 seconds old may effectively receive only around 31 seconds before force-close. Existing streams lasting beyond 5 minutes and 30 seconds are also terminated.

**Impact**

- Long reasoning streams, generation streams, video operations, or slow-provider operations terminate before their configured route deadline.
- Clients can receive a transport EOF or reset rather than a meaningful provider or route-timeout error.
- The configuration contract contradicts the actual listener-level SLA.

**Fix**

When connection age is reached, send HTTP/2 GOAWAY to prevent new streams, but allow active streams to continue until their individual route deadlines.

Alternatively, restrict route timeouts to a maximum that the transport can actually guarantee and expose that restriction clearly in the API and console.

## 7. [Medium] The concurrency lease uses the maximum timeout of every route visible to the API key before route selection

**Evidence**

- `apps/olp/src/request_admission/limits.rs:286-316`
- Route timeout range described in finding 6

The initial admission lease TTL is not based on the route eventually selected. Instead, it iterates over every route accessible to the API key and uses the longest timeout plus 60 seconds.

**Impact**

A single misconfigured 24-day route causes short chat requests, list requests, and even requests that later fail validation to acquire extremely long crash-recovery leases.

If the process dies before releasing the lease, a concurrency slot can remain occupied for weeks.

**Fix**

Acquire a short provisional lease, then atomically extend it after route selection using the selected route’s deadline.

The maximum configurable route timeout should also be reduced to an operationally realistic value.

## 8. [Medium, Static Edge Case] Extreme usage timestamps can panic and produce a caught 500 response

**Evidence**

- `apps/olp/src/operations/usage.rs:15-51`
- `apps/olp/src/operations/helpers.rs:30-45`
- `crates/storage/src/usage/query.rs:141-152`
- `apps/olp/src/router.rs:172,289-293`

Query validation checks ordering and range length, but does not verify that Unix timestamps are representable by Chrono.

The storage layer uses `DateTime::from_timestamp(...).expect(...)` and performs unchecked addition when calculating the hour ceiling.

**Impact**

An `i64` timestamp that is syntactically valid but outside Chrono’s representable range can panic. The router’s panic catcher prevents whole-process termination, but the client receives a 500 instead of a 400, and panic logs and metrics are polluted.

**Fix**

Perform checked timestamp conversion at the API boundary and enforce an operationally reasonable date range. Remove `expect` and unchecked duration addition from this path.

## 9. [Low] Invalid OIDC `return_to` values silently fall back instead of returning an error

**Evidence**

- `apps/olp/src/oidc/authorization.rs:85-107,125-148`

GET query parsing failures and explicitly invalid `return_to` validation failures are discarded using `.ok()`, and the user is redirected to the default path.

**Impact**

The implementation blocks open redirects, but it also hides broken client integrations and corrupted URLs. Users land on an unexpected default page with no indication of what failed.

**Fix**

Use the default only when the parameter is absent. If the parameter is present but malformed or invalid, return a 400 problem response.

## 10. [Medium, Conditional] Persistent media spool storage leaks orphan directories and resets capacity accounting after crashes

**Evidence**

- `apps/olp/src/media_spool.rs:62-81,375-378`
- Default deployment mitigation:
  - `deploy/helm/templates/workloads.yaml:180-182`
  - `deploy/compose.yaml:38-43`
- Persistent/custom paths are supported:
  - `docs/configuration.md:24-25`

The spool root is newly created on each startup using `olp-media-<pid>-<uuid>`, and `used_bytes` starts at zero. Cleanup depends on `Drop`.

`Drop` does not run after SIGKILL, OOM termination, or node power loss.

The default Helm and Compose configurations use ephemeral storage, which reduces the impact. However, when users configure a persistent or custom directory as documented, the new process ignores old directories and allocates the full configured capacity again.

**Fix**

On startup, scan and scavenge prior spool directories and reconstruct filesystem accounting.

Alternatively, use a fixed root with manifests and leases instead of a random per-process root. Filesystem quotas should be used as the final safety boundary.

## 11. [Low] The IPv6 global-unicast allowlist is a dated source-code snapshot

**Evidence**

- `crates/providers/src/http_egress.rs:47-105`

The code contains an IPv6 positive allowlist annotated as current “as of 2026-07.”

**Impact**

Future IANA allocation changes can cause legitimate endpoints to be rejected as security violations. SSRF correctness depends on release cadence and manual awareness of registry changes.

**Fix**

Generate a verified IANA registry snapshot during the build, or consider maintaining a strict denylist of special-purpose, loopback, link-local, documentation, and other non-global ranges rather than a positive global-unicast list.

Add a registry-freshness test.

## 12. [Medium] The concurrency lease remains held until the client finishes reading the response body

**Evidence**

- `apps/olp/src/request_admission.rs:665-673`
- `apps/olp/src/request_admission/limits.rs:144-172`
- Connection-lifetime behavior in `apps/olp/src/listener.rs`

The accounting guard is attached to the response-body lifecycle. A slow client, or a client that stops reading, continues occupying a concurrency slot even after upstream computation has completed.

**Impact**

A slow reader within a tenant or API key can easily cause self-DoS. The quota measures “response delivery until client egress completes” rather than “concurrent upstream work.”

**Fix**

Release the concurrency lease when the upstream operation completes.

Client egress and backpressure should be controlled using separate body/connection timeouts or a separate quota.

## 13. [Low, Explicit Performance Debt] HTTP/1 keep-alive is globally disabled

**Evidence**

- `apps/olp/src/listener.rs:279-287`

The listener uses `.keep_alive(false)` to preserve an exact raw-header bound for the first request.

**Impact**

HTTP/1 clients create a new TCP/TLS/proxy connection for every request. This unnecessarily increases CPU usage and tail latency under high QPS, cross-region TLS, or sidecar-proxy deployments.

**Fix**

Implement request-specific parser/header bounds or enforce H1 normalization at a trusted edge proxy.

If the current behavior is retained, document the HTTP/1 connection churn and expose a corresponding operational metric.

## 14. [High] Pricing lookup prioritizes provider-specific entries over the latest revision

**Evidence**

- `crates/storage/src/request_metadata/ingestion.rs:337-346`
- Revision UI semantics:
  - `console/src/lib/features/settings/SettingsPage.svelte:124`

The core ordering in the pricing-selection SQL is:

```sql
ORDER BY (price.provider_id IS NOT NULL) DESC,
         revision.effective_at DESC,
         revision.revision DESC
LIMIT 1
```

Suppose a January revision contains a provider-specific override and a February revision contains only a newer generic price. A request in March still selects the January provider-specific override because provider specificity is sorted before revision freshness.

**Impact**

- Old overrides can survive indefinitely after a new price revision is activated.
- Cost reports, budget alerts, and chargeback calculations silently become incorrect.
- Runtime behavior contradicts the product’s immutable-revision model.

**Fix**

First select exactly one latest revision that is effective at the request timestamp. Then, within that revision, apply provider-specific-over-generic fallback.

If provider overrides are intentionally independent of revisions, the schema and UI should model them as separate persistent rules.

## 15. [Medium, Policy Ambiguity] Pricing is selected using request completion time rather than request start time

**Evidence**

- `crates/storage/src/request_metadata/ingestion.rs:341`
- `apps/olp/src/gateway/telemetry.rs:471-497`

The `observed_at` value passed to pricing lookup is the request completion timestamp.

**Impact**

A long-running request that crosses a pricing-revision activation boundary is billed using the price active when it finishes rather than the price known when it began.

This is visible for long streams and media operations.

**Fix**

For the usual cost contract, snapshot pricing using `request_started_at`.

If completion-time pricing is intentional, document it in the API, UI, and audit log and preserve the behavior with explicit tests.

## 16. [Medium] Cached input tokens are stored, but the pricing model cannot represent or calculate cached-token rates

**Evidence**

- `crates/storage/src/request_metadata/ingestion.rs:331-334`
- `crates/storage/src/operations/pricing.rs:22-31`
- `apps/olp/src/gateway/telemetry.rs:357-375,389-446`
- `crates/protocols/src/openai/client.rs:99-108`

Canonical usage and the database both include `cached_input_tokens`, but the pricing model only contains input, output, and unit prices.

The cost calculation multiplies all `input_tokens` by the normal input rate.

**Impact**

For providers that discount prompt-cache hits, calculated cost is higher than the provider’s actual charge. Budget enforcement and customer chargeback become financially incorrect.

**Fix**

Add a cached-input unit price to the pricing-revision schema and calculate:

```text
(input_tokens - cached_input_tokens) * normal_input_price
+ cached_input_tokens * cached_input_price
```

The invariant in finding 27 must be enforced before this calculation is introduced.

## 17. [High] The video-list API can trigger up to 100 upstream reads and database writes while racing the background reconciler

**Evidence**

- `apps/olp/src/gateway/videos.rs:342-415`
- `apps/olp/src/gateway/media_jobs.rs:141-165,435-497`
- `crates/storage/src/media_jobs/reconciliation.rs:44-107`

The list endpoint reads up to 100 records, then performs an upstream `VideoGet` for every queued or running item and updates the database.

Concurrency is limited to four, but total fan-out is still up to 100.

A separate autonomous reconciler already polls active jobs every five seconds and uses database claims. The list-refresh path does not acquire those claims, so it can query and update the same job concurrently with the reconciler.

Upstream and authorization failures are silently replaced with stale records, and the endpoint still returns 200.

**Impact**

- One `GET /videos` request can cause up to 100 provider API calls and database writes.
- Multiple users refreshing the list amplify provider cost and rate-limit usage.
- The path bypasses background claim coordination, producing duplicate polling and last-writer races.
- Errors are hidden as stale success, so the UI cannot determine freshness.
- If each internal lookup emits request metadata, analytics become polluted by list refreshes.

**Fix**

Make the list endpoint return only the database snapshot and assign polling ownership exclusively to the background reconciler.

Expose fields such as `last_polled_at`, `stale`, and `refresh_error_class` if freshness information is required.

If an explicit refresh endpoint is necessary, it should acquire per-job claims and process only a very small bounded batch.

## 18. [Medium] Several management list APIs perform hundreds of database round trips per page

**Evidence**

- API keys:
  - `crates/storage/src/configuration/resources/api_keys.rs:4-53`
- Route drafts:
  - `crates/storage/src/configuration/resources/routes.rs:4-53`
- Routes/revisions:
  - `crates/storage/src/configuration/resources/routes.rs:360-418`
- Existing comparable batch implementation:
  - `crates/storage/src/configuration/resources/models.rs:111-150`

For example, the API-key list first fetches IDs and then performs separate queries for each key’s base row, scopes, and routes.

At a page size of 100, this is approximately 301 round trips. Route drafts use a similar pattern.

**Impact**

The problem may remain hidden when PostgreSQL is local, but cross-AZ PostgreSQL, pool contention, and console startup expose severe tail-latency growth. Query count scales linearly with page size.

**Fix**

Fetch base rows in one query, batch-fetch child rows using `WHERE id = ANY($1)`, and group the results in memory.

A large generic ORM abstraction is unnecessary. Explicit resource-specific two- or three-query implementations are preferable to the current N+1 loops.

## 19. [Low] The invitation dialog displays a different value from the one copied by the button

**Evidence**

- `console/src/lib/features/access/AccessPage.svelte:273-289,330-334`

The copy button places a fragment-safe full invitation URL on the clipboard, but the visible field displays only the raw bearer token. The full URL is shown only after clipboard failure.

**Impact**

A user who manually selects and copies the visible value sends a token rather than a usable link.

The interface says “Copy invitation link,” but its visible representation does not match that behavior and unnecessarily exposes the bearer secret.

**Fix**

Always display the full URL in a read-only field and hide the raw token by default.

If both URL and token must be provided, present them as clearly separate values.

## 20. [Low] `source_draft_id` points to a mutable draft and cannot preserve exact route-revision provenance

**Evidence**

- `crates/storage/src/configuration/resources/routes.rs:56-237`
- Repeated activation is intentional:
  - `crates/storage/tests/integration/configuration_postgres.rs:460-488`
- `crates/storage/tests/integration/route_draft_simulation_postgres.rs:138-154`

Activation copies values into an immutable runtime revision, so runtime behavior itself is stable.

However, `source_draft_id` points to a draft that can later be modified, revalidated, and activated again. The reference prevents deletion but does not preserve the draft contents at activation time.

**Impact**

It is impossible to reconstruct exactly which draft input produced a historical revision. During audits or incident investigations, the source pointer can be misleading.

**Fix**

Create an immutable draft snapshot/version for every activation, or store the canonical source document and hash directly on the revision record.

## 21. [Medium, Security-State Inconsistency] Logout returns 204 even when database session revocation fails

**Evidence**

- `apps/olp/src/management_api/auth.rs:435-465`
- `crates/storage/src/store/sessions.rs:198-229`

Logout clears the browser cookie, but a failure in `revoke_session_by_token` is only logged as a warning, and the endpoint still returns 204.

A comment describes this as fail-closed in the browser, but the server-side session has not actually been revoked.

**Impact**

The current browser appears logged out, but a stolen copy of the same session cookie remains valid until expiration.

A user attempting incident response through logout can incorrectly believe the server credential was invalidated.

**Fix**

Always clear the local cookie, but return 503 or an explicit `server_revocation_failed` response when server-side revocation fails.

For stronger security, use a durable revocation mechanism such as a user/session security version or a revocation retry outbox.

## 22. [High] Maintenance performs large rollups and deletions in one unbounded transaction

**Evidence**

- `crates/storage/src/maintenance.rs:46-312`

One transaction performs all of the following:

- Deletes all old requests
- Aggregates and deletes expired usage facts
- Deletes audit events
- Deletes sessions
- Deletes invitations
- Deletes idempotency rows
- Deletes OIDC flows
- Deletes outbox rows
- Deletes media jobs

Only request-metadata receipts use a 250,000-row batch. Most other operations have no row bound.

**Impact**

During the first cleanup after a large deployment or retention-policy change, this can cause:

- Very long transactions
- Massive WAL generation
- Long-lived row or table locks
- Delayed autovacuum
- Replica lag
- Statement timeouts
- Full rollback if a late stage fails
- Repetition of the same expensive work in the next cycle

**Fix**

Split each data group into a separate transaction with bounded batches and a persistent progress watermark.

Use patterns such as:

```sql
DELETE FROM ...
WHERE id IN (
    SELECT id
    FROM ...
    WHERE ...
    ORDER BY ...
    LIMIT n
)
```

Alternatively, use a time/key cursor. Rollup and deletion should also commit incrementally.

## 23. [Medium, Cost and Idempotency Risk] Ordinary generation retries another provider after first-byte ambiguity

**Evidence**

- `apps/olp/src/gateway/failover.rs:214-262,282-348,441-469`
- Behavior-preserving test:
  - `apps/olp/src/gateway/tests/failover.rs:210-226`

Image, audio, and video operations explicitly prevent ambiguous retries because their side effects are obvious.

Ordinary generation is not treated as side-effecting. If the request reached the provider and was generated and billed, but the first response byte was delayed or lost, the gateway can send the request again to another target.

**Impact**

The client receives one answer while the operator may pay two providers.

Generation can also include tool calls, provider-side logging, and retention, so it is not equivalent to retrying a pure read operation.

**Fix**

Provide route-level policies such as:

- `at_most_once`
- `availability_first`

Make the default explicit.

Forward idempotency keys where providers support them. Another option is to expose first-byte ambiguity as a distinct error and allow the caller to decide whether to retry.

## 24. [Medium] Five provider 429 responses open a process-local target circuit for 30 seconds

**Evidence**

- `apps/olp/src/gateway/failover.rs:100-105`
- `apps/olp/src/circuit.rs:9-10,95-156`

Canonical rate-limit failures are counted as circuit failures. At a threshold of five, the runtime target circuit opens for 30 seconds.

**Impact**

A rate limit scoped to one credential, model, tenant, or request class can block unrelated local traffic using the same target.

Because circuit state is replica-local, one replica can block traffic while another continues sending requests.

The implementation also ignores the provider’s actual `Retry-After` value.

**Fix**

Separate 429 handling from transport and 5xx circuit breaking.

Maintain provider/model/credential-scoped rate-limit backoff and honor `Retry-After`.

The health circuit should primarily track target-health signals such as connection failures, timeouts, and 5xx responses.

## 25. [Medium/Low] DNS refresh occurs while holding one async mutex, serializing provider tail latency

**Evidence**

- `crates/providers/src/http_egress/pinned.rs:92-143`

`PinnedClientPool` holds its cache mutex while performing DNS resolution and constructing the client.

After cache expiration, one slow DNS lookup causes every waiter for the same provider to queue behind the mutex.

**Impact**

DNS tail latency becomes provider-wide request-preparation latency. The preparation timeout for each waiting request is consumed by both lock wait and actual DNS resolution.

**Fix**

Use a double-checked cache and a shared in-flight refresh future.

Another option is to read the cache generation, resolve outside the lock, and publish the result with a compare-and-swap-like generation check.

The existing SSRF validation and address pinning must remain intact.

## 26. [Low] Console `collectAllCursorPages` loads up to 10,000 records sequentially and fails only after exceeding the limit

**Evidence**

- `console/src/lib/api/pagination.ts:27-57`

The helper sequentially fetches every cursor page and appends the results to one array.

It throws only after receiving and appending a page that pushes the total beyond 10,000.

The helper is used for several provider, route, and API-key selection flows.

**Impact**

As data grows, the UI performs hundreds of sequential HTTP round trips, consumes large amounts of memory, and eventually hard-fails at the 10,001st record.

**Fix**

Use server-side search or autocomplete with virtualized selectors.

At minimum, enforce page and cumulative-row limits before fetching the next page and render incrementally.

## 27. [Medium] The invariant `cached_input_tokens <= input_tokens` is not enforced in the application or database

**Evidence**

- `crates/storage/src/request_metadata/ingestion.rs:100-149,357-366`
- `crates/storage/migrations/0001_initial.sql:345-368`
- `apps/olp/src/gateway/telemetry.rs:357-367,394-407,423-446`

Current validation checks only that values are non-negative and representable.

A broken provider adapter can report more cached input tokens than total input tokens, and the value will be stored.

**Impact**

Usage reports can contain logically impossible values.

If cached-token discounts are later implemented as described in finding 16, `(input_tokens - cached_input_tokens)` can become negative and corrupt cost calculations.

**Fix**

Enforce the relationship in all three layers:

1. Canonical protocol conversion
2. Ingestion validation
3. Database constraint

For example:

```sql
CHECK (
  cached_input_tokens IS NULL
  OR (input_tokens IS NOT NULL AND cached_input_tokens <= input_tokens)
)
```

## 28. [Medium] Retention cleanup lacks supporting partial indexes and can repeatedly perform full scans

**Evidence**

- Invitation cleanup:
  - `crates/storage/src/maintenance.rs:250-256`
- Invitation indexes:
  - `crates/storage/migrations/0003_identity_management.sql:25-28`
- Deleted-media cleanup:
  - `crates/storage/src/maintenance.rs:286-293`
- Media indexes:
  - `crates/storage/migrations/0007_async_media_job_lifecycle.sql:21-29`
  - `crates/storage/migrations/0014_async_media_reconciliation.sql:36-38`
  - `crates/storage/migrations/0018_async_media_durability.sql:47-53`

Maintenance deletes:

- Invitations where `accepted_at IS NULL AND expires_at <= ...`
- Media jobs where `lifecycle_state='deleted' AND deleted_at < ...`

No index directly supports either cleanup predicate. Existing reconciliation indexes exclude deleted rows.

**Impact**

As the tables grow, periodic maintenance can combine sequential scans with large deletes, worsening the long-transaction problem described in finding 22.

**Fix**

Add partial indexes such as:

```sql
CREATE INDEX ... ON invitations(expires_at)
WHERE accepted_at IS NULL;

CREATE INDEX ... ON async_media_jobs(deleted_at)
WHERE lifecycle_state = 'deleted';
```

Validate them using real cardinalities and `EXPLAIN (ANALYZE, BUFFERS)`.

## 29. [Medium] Upstream `Retry-After` is neither parsed nor propagated

**Evidence**

- OpenAI:
  - `crates/providers/src/openai/transport/operations/http.rs:275-291`
- Anthropic:
  - `crates/providers/src/anthropic/transport/operations.rs:372-388`
- Gemini:
  - `crates/providers/src/gemini/transport/operations.rs:452-468`
- Gateway mapping:
  - `apps/olp/src/gateway/error.rs:206-212`

Each provider adapter reads the status and body and classifies 429 responses, but discards the `Retry-After` header.

The final gateway error contains `retry_after: None`.

**Impact**

Clients and internal proxies cannot use the provider’s exact backoff instruction. This contributes to retry storms and leaves the system relying on the arbitrary 30-second circuit behavior from finding 24.

**Fix**

Safely parse both:

- Delta-seconds form
- HTTP-date form

Apply a reasonable maximum, preserve the value in the typed transport error, expose it to the client, and reuse it in provider/model/credential rate-limit state.

## 30. [Medium] A pricing revision accepts 10,000 entries while issuing one or two database queries per entry

**Evidence**

- `crates/storage/src/operations/pricing.rs:127-160,287-291`

While holding a transaction and advisory lock, the implementation loops over every price entry.

For each entry with a provider, it performs one provider-kind lookup and then one row insertion.

At the maximum of 10,000 entries, this can produce approximately 20,000 database round trips.

**Impact**

- Long advisory-lock duration
- Long transaction duration
- Connection-pool occupation
- Transaction timeout
- Increased WAL latency
- A single management request can monopolize database resources for an extended period

**Fix**

Fetch all provider IDs and kinds in one query, construct a map, and insert price rows using `UNNEST`, multi-row insertion, or COPY.

The request maximum should also be reduced to a realistic operational bound.

## 31. [Low] Pricing-revision POST returns unnormalized input while the database stores normalized values

**Evidence**

- Normalization and insertion:
  - `crates/storage/src/operations/pricing.rs:143-157`
- Response and idempotency payload:
  - `crates/storage/src/operations/pricing.rs:172-190`
- List results:
  - `crates/storage/src/operations/pricing.rs:247-273`

Before insertion, the model name is trimmed and the currency is uppercased.

However, the creation response uses `prices.to_vec()`, returning the original unnormalized input. Idempotency replay preserves the same unnormalized response. A later GET returns the normalized database representation.

**Impact**

The same resource has different representations immediately after POST and after GET.

This destabilizes client caches, equality checks, and audit output.

**Fix**

Construct normalized records first and use the same values for insertion and response generation.

Alternatively, build the response from `INSERT ... RETURNING`.

## 32. [Medium] Media-reconciliation claims last two minutes while route requests can run for tens of days

**Evidence**

- Incorrect comment and fixed lease:
  - `crates/storage/src/media_jobs/reconciliation.rs:41-43,80-85`
- Claim ownership check:
  - `crates/storage/src/media_jobs/reconciliation.rs:112-140`
- Actual provider-operation timeout:
  - `apps/olp/src/gateway/media_jobs.rs:346-367`
- Route timeout range:
  - See finding 6

A comment claims that the database lease is intentionally longer than an ordinary route deadline, but the implementation uses a fixed two-minute lease.

Route timeouts can be configured up to approximately 24.85 days, and there is no heartbeat or claim extension.

**Impact**

If an upstream `VideoGet` or delete request takes longer than two minutes, another replica can claim the same job and issue a duplicate provider request.

The first worker later fails `finish_media_reconciliation` because the claim ID changed.

Even when deletion itself is idempotent, provider rate limits, request metadata, retry state, and operational cost can be duplicated.

**Fix**

Apply a realistic maximum route timeout and derive claim TTL from that maximum plus a safety margin.

Alternatively, heartbeat and extend the claim periodically while the provider operation is running.

Add a test that verifies the comment’s intended lease/deadline relationship.

# Code and Design That Qualify as Particularly Bad

These are not mere style complaints. They materially increase maintenance cost or amplify failures.

## A. Quota lifecycle is scattered across manual cleanup paths

The lifecycle:

```text
reserve
-> validate
-> select route
-> execute
-> stream/drop
-> reconcile/release
```

is distributed across several guards and optional-usage branches instead of being represented as one explicit state machine. This directly contributes to findings 2 through 5.

The problem is not simply “insufficient abstraction.” The resource-lifecycle abstraction exists at the wrong boundary.

A single `AdmissionLease` should not loosely mix token and concurrency state. Each resource should have an idempotent state transition with explicit ownership.

## B. The video-list endpoint acts as a reconciliation engine inside a read API

Finding 17 is the worst form of responsibility mixing.

A read path performs:

- Provider polling
- Failover
- Authorization
- Telemetry
- Database mutation

A dedicated background reconciler already performs the same responsibility.

This code should not be optimized. It should largely be deleted, and the endpoint should return a database-only list.

## C. Handwritten N+1 loops in management APIs

Findings 18 and 30 go beyond the point where simple code is beneficial.

Database round trips scale directly with API payload size because the repository layer lacks batch semantics.

A large generic ORM or repository abstraction is unnecessary, but explicit resource-specific operations such as `fetch children for ids` are required.

## D. Contradictory timeout and lease constants

The current system contains:

- Transport connection age: five minutes plus 30 seconds
- Media claim duration: two minutes
- Route timeout: up to approximately 24.85 days
- Initial concurrency TTL: maximum timeout of every visible route plus 60 seconds

Each subsystem may have selected a locally “safe” constant, but the composed system has no coherent deadline contract.

There should be one bounded request deadline as the source of truth. Transport lifetime, concurrency lease, reconciliation claim, and cleanup margin should be derived from it.

## E. Immutable revision semantics are destroyed by one lookup ordering

The pricing schema attempts to model immutable revisions, but the SQL in finding 14 invalidates the entire semantic model through two ordering priorities.

Revision selection and provider fallback should not be mixed in one `ORDER BY`.

Use a two-stage query or CTE:

1. Select the applicable latest revision.
2. Select provider-specific or generic pricing within that revision.

## F. Maintenance is implemented as one “finish everything” transaction

Finding 22 may appear clean in a small installation, but it is one of the worst possible designs as operational data grows.

Maintenance is not an atomic business transaction. It should be a bounded, restartable, and observable batch job.

# Suspected Findings That Were Investigated and Excluded

The following initially appeared problematic, but deeper source and test inspection showed that the claims were unsupported or incorrect.

1. **Request-metadata shutdown can misreport success because of a 100 ms race**

   Excluded because the final checkpoint verifies both that the writer is closed and that pending work is zero.

2. **`RequestAccountingGuard::disarm` leaks reservations**

   Excluded because a task-local hold path preserves ownership. A leak could not be established.

3. **A streaming attempt is permanently marked successful after the first byte**

   Excluded because the final emitter overwrites status, completion state, and latency using the actual terminal state of the last attempt.

4. **Media side-effect operations are always duplicated by failover**

   Excluded because ambiguous retries for image, audio, and video operations are separately blocked and tested.

   Finding 23 applies specifically to ordinary generation.

5. **Egress is trivially vulnerable to DNS rebinding or redirect-based SSRF**

   Excluded because redirects, proxies, and client retries are disabled; all resolved addresses are validated; and DNS results are pinned.

   This area is comparatively robust.

6. **Pricing cursors can return only some price rows for a revision**

   Excluded because the implementation first selects `limit + 1` revisions and then joins all child prices for the selected revisions.

7. **Double burst at minute boundaries is an implementation bug**

   Excluded because the architecture documentation explicitly specifies fixed UTC-minute windows.

   It remains a product limitation for users expecting a sliding-window limiter.
