# MiniMax inference and remains evidence

This note checks the remaining evidence for [#642](https://github.com/tyk-swe/olp/issues/642) and [#647](https://github.com/tyk-swe/olp/issues/647), using public MiniMax documentation and the vendor's CLI source. Sources were observed on 2026-11-05 UTC. No live inference or remains requests, account access, or credentials were used.

## Inference quota errors and replay

The [error catalog](https://platform.minimax.io/docs/api-reference/errorcode) identifies `2056` as a usage limit and `2067` as a usage limit with automatic credit consumption disabled. It describes `2062` as a rate limit that can also indicate no active subscription when querying usage. These meanings alone do not establish a response envelope or prove a request was not executed.

The [Chat Completions OpenAPI schema](https://platform.minimax.io/docs/api-reference/text/api/openapi-chat-openai.json) declares `base_resp.status_code` as an error field and refers readers to the general error catalog. That is a connection between this endpoint and the catalog, but the schema does not explicitly place `2056` or `2067` in a Chat Completions response. The [Messages OpenAPI schema](https://platform.minimax.io/docs/api-reference/text/api/openapi-chat-anthropic.json) describes HTTP and streaming errors with `error.type` and `error.message`, without declaring numeric `error.code`. Its omission is not proof that an additional field can never be sent.

The vendor CLI [declares](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/errors/api.ts#L4-L15) and [reads](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/errors/api.ts#L33-L40) both `base_resp.status_code` and `error.code`, and its [text SDK](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/sdk/text/index.ts#L34-L48) uses the Messages endpoint. Separately, [MiniMax Code](https://github.com/MiniMax-AI/minimax-code/blob/3c21163c85a9684030cb147bfef48c6284fa3c46/packages/shared/src/llm-error-classifier.ts#L858-L869) classifies `2056` and `2067` from an upstream `status_code`. Its [retry test](https://github.com/MiniMax-AI/minimax-code/blob/3c21163c85a9684030cb147bfef48c6284fa3c46/packages/agent-core/test/unit/pi-turn-runner/llm-retry.test.ts#L362-L382) uses synthetic top-level status codes. These sources show client behavior, not an observed quota rejection in either CLI-declared inference envelope.

A [user report in the vendor repository](https://github.com/MiniMax-AI/MiniMax-M2.7/issues/36) describes a Messages error with `2056` in `error.message`. It does not show a numeric `error.code` and is not vendor-issued evidence. No first-party source found proves that Chat Completions or Messages emits `2056` or `2067` in either numeric envelope or that such a rejection guarantees non-execution. The replay evidence needed for #642 remains unmet.

## Remains endpoint and regional fixtures

The current [global M Plan FAQ](https://www.minimax.io/m-plan) gives `https://www.minimax.io/v1/token_plan/remains` for an authenticated usage read. The corresponding [mainland FAQ](https://www.minimax.cn/m-plan) gives `https://www.minimax.cn/v1/token_plan/remains`. Both provide request examples and neither provides a real-key response fixture. The examples appear in the pages' delivered HTML.

The vendor CLI's [region configuration](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/config/schema.ts#L1-L4) instead sets the regional bases to `https://api.minimax.io` and `https://api.minimax.cn`. Its [endpoint selection](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/client/endpoints.ts#L49-L92) appends `/v1/token_plan/remains` for non-`sk-api-` API keys and OAuth credentials. The [setup code](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/commands/agent/setup.ts#L118-L135) identifies `sk-cp-` as a token plan key. The [quota SDK](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/sdk/quota/index.ts#L18-L29) passes the selected URL to the shared HTTP client, which defaults to [bearer authorization and GET](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/client/http.ts#L111-L145). CLI HEAD was `38aba5f26173dd1065b115b221d79c9ddd87c6bb` on the observation date.

The documented `www` hosts and the CLI's `api` hosts differ. These sources do not establish whether either CLI host fails, whether the hostnames are interchangeable, or whether a given region and key produce the expected response. No change in host or profile qualification follows from that difference alone.

The CLI ships a [quota response fixture](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/test/fixtures/quota-response.json) and [response types](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/types/api.ts#L337-L373), but neither identifies a real key, the region used to obtain a response, or the fixture's provenance. The [SDK quota test](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/test/sdk/quota.test.ts#L62-L95) returns its example from a local mock server. These are evidence of client expectations, not authenticated real-key fixtures.

A [user report in the CLI repository](https://github.com/MiniMax-AI/cli/issues/53) includes an example JSON response and says its region is `cn`, but does not identify an `sk-cp-` key. A [different user report](https://github.com/MiniMax-AI/cli/issues/165) shows a partial `general` row and describes both regions, but does not provide a complete response for each region from a known `sk-cp-` key. These are user-authored reports, not vendor-issued schema guarantees.

No source found supplies the required authenticated real-key response fixture for either global or mainland. The real-key fixture path for #647 therefore remains unmet for both profiles. The ticket also permits explicit exclusion of an unpinned profile, which is a separate implementation decision. This investigation does not qualify ordering from remains observations.
