# MiniMax and Kimi vendor client signals

Status, research note, fetched 2026-11-05. Facts below come from primary sources only, meaning the vendor client source trees named here and the tests and fixtures that ship inside them. Each claim names its source so a reader can tell stale from broken

Pinned sources are [MiniMax-AI/cli at 38aba5f](https://github.com/MiniMax-AI/cli/tree/38aba5f26173dd1065b115b221d79c9ddd87c6bb) and [MoonshotAI/kimi-code at df90d90](https://github.com/MoonshotAI/kimi-code/tree/df90d90ec0714db23dcc830acd2db6232f5c7426). Both shas are the HEAD commits returned by the GitHub commits API for those repos on the fetch date, and every blob link below pins the same sha

The short version is that the MiniMax CLI now proves the remains schema that the fetched vendor pages left open, including millisecond epoch window bounds, per window counts, and optional server remaining percents. It also proves that one error mapper reads two different upstream envelopes for every command, quota and chat alike. The Kimi Code client proves something narrower and still useful, which is that upstream chat errors are classified from the OpenAI and Anthropic SDK error objects by status plus a structured code or type, and never by matching the documented quota wording

## MiniMax remains endpoint selection

Base URLs come from a two entry region table. Region `global` is `https://api.minimax.io` and region `cn` is `https://api.minimax.cn`, with an explicit base URL override winning over the region when one is configured. The table is [`REGIONS`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/config/schema.ts#L1-L4) in `src/config/schema.ts`, and endpoint builders only ever append a fixed path to whatever base URL resolved

Two usage endpoints hang off that base. [`quotaEndpoint`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/client/endpoints.ts#L49-L51) appends `/v1/token_plan/remains`, and [`accountBalanceEndpoint`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/client/endpoints.ts#L53-L55) appends `/account/query_balance` with no `/v1` segment. Both live in `src/client/endpoints.ts`, so the four exact URLs are `https://api.minimax.io/v1/token_plan/remains` and `https://api.minimax.cn/v1/token_plan/remains` for the token plan read, plus `https://api.minimax.io/account/query_balance` and `https://api.minimax.cn/account/query_balance` for the account balance read. The region tests pin the two remains URLs and a custom base URL case in [`endpoints.test.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/test/client/endpoints.test.ts#L4-L16)

Credential kind picks between those two endpoints, and the test is a prefix plus an auth method, nothing more. [`isSecretApiKey`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/client/endpoints.ts#L57-L59) returns true exactly when the token starts with `sk-api-`, and [`selectUsageEndpoint`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/client/endpoints.ts#L61-L88) returns kind `account-balance` only when the credential method is `api-key` and that prefix matches. Every other credential returns kind `quota`, which covers token plan API keys that lack the prefix and every OAuth credential. An OAuth access token that happens to start with `sk-api-` still takes the remains endpoint, and that case has its own SDK test in [`quota.test.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/test/sdk/quota.test.ts#L165-L202)

The credential fed into that choice comes from [`resolveCredential`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/auth/resolver.ts#L9-L32) in `src/auth/resolver.ts`, which prefers a flag API key with method `api-key`, then stored OAuth credentials after a freshness refresh with method `oauth`, then a config file API key with method `api-key`. Both callers resolve first and select second, namely [`QuotaSDK.info`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/sdk/quota/index.ts#L18-L29) in `src/sdk/quota/index.ts` and the `quota show` command in [`show.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/commands/quota/show.ts#L26-L41). A legacy helper named `usageEndpoint` wraps the same selection by forcing method `api-key`, so callers that only hold a raw key string get balance for `sk-api-` keys and remains for everything else, in [`endpoints.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/client/endpoints.ts#L90-L92)

Auth on the wire is a bearer token for both usage calls. Neither caller passes an `authStyle`, so [`request`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/client/http.ts#L99-L124) in `src/client/http.ts` falls into its default branch and sends `Authorization: Bearer {token}` with `Content-Type: application/json`. The SDK quota tests assert that header and assert that no `x-api-key` header is sent, for a regular key in [`quota.test.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/test/sdk/quota.test.ts#L62-L95) and for an `sk-api-` key in the same file at [`quota.test.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/test/sdk/quota.test.ts#L97-L130). Both calls pass only a URL, so the HTTP method is the `GET` default in [`request`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/client/http.ts#L142-L153)

One related probe is worth separating from the quota read itself. Region detection reuses the same selected usage URL per region, tries bearer auth and then `x-api-key` auth against both regional hosts, and calls a region authorized only when the JSON answer carries `base_resp.status_code` equal to 0. That probe is [`probeRegion`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/config/detect-region.ts#L9-L58) in `src/config/detect-region.ts`, so the remains and balance endpoints both double as a credential region test inside this client

## MiniMax remains response shape and units

The typed answer is deliberately thin at the top. [`QuotaResponse`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/types/api.ts#L337-L339) in `src/types/api.ts` declares only `model_remains` as an array of `QuotaModelRemain`. A `base_resp` envelope field still arrives on the wire per the shipped fixture and is checked generically by the HTTP layer, but it is not part of the `QuotaResponse` type. The balance answer is typed separately as [`AccountBalanceResponse`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/types/api.ts#L341-L350), which carries `available_amount`, `cash_balance`, `voucher_balance`, `credit_balance`, and `owed_amount` as strings, plus a `balance_alert_switch` boolean, a `balance_alert_threshold` string, and a required `base_resp`. The shared envelope type is [`BaseResp`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/types/api.ts#L418-L421) with a numeric `status_code` and a string `status_msg`

Every `QuotaModelRemain` field is a TypeScript `number` apart from `model_name`, and the full declaration sits in [`QuotaModelRemain`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/types/api.ts#L352-L373). Reading the consumption sites back into that type gives the unit for each field

| Field | Type | Unit or meaning the client assumes |
|---|---|---|
| `model_name` | string, required | bucket name, rendered verbatim |
| `start_time` | number, required | interval start as a millisecond epoch |
| `end_time` | number, required | interval end as a millisecond epoch |
| `remains_time` | number, required | milliseconds until the interval ends, a duration and not an epoch |
| `current_interval_total_count` | number, required | interval total count, unitless count |
| `current_interval_usage_count` | number, required | reported interval count whose remaining or used meaning is ambiguous |
| `current_interval_remaining_percent` | number, optional | server remaining percent for the interval |
| `current_weekly_total_count` | number, required | weekly total count, unitless count |
| `current_weekly_usage_count` | number, required | reported weekly count with the same ambiguity |
| `current_weekly_remaining_percent` | number, optional | server remaining percent for the weekly window before any boost |
| `current_interval_status` | number, optional | 1 normal, 2 exhausted, 3 unlimited per the type comment |
| `current_weekly_status` | number, optional | same status enum for the weekly window |
| `weekly_start_time` | number, required | weekly window start as a millisecond epoch |
| `weekly_end_time` | number, required | weekly window end as a millisecond epoch |
| `weekly_remains_time` | number, required | milliseconds until the weekly window ends, a duration and not an epoch |
| `weekly_boost_permille` | number, optional | weekly display multiplier in permille, where 1500 renders the base percent at one and a half times |

The millisecond reading is proven three ways inside the pinned tree rather than guessed from field names. [`formatDate`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/output/quota-table.ts#L71-L73) in `src/output/quota-table.ts` names its parameter `epochMs` and passes it straight to `new Date(epochMs)` for the weekly range header, while [`formatDuration`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/output/quota-table.ts#L50-L56) divides `remains_time` by 3600000 and 60000 as a millisecond duration. The shipped fixture then agrees numerically, since `start_time` 1776355200000 in [`quota-response.json`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/test/fixtures/quota-response.json#L6-L21) is a 2026 millisecond epoch, and the same fixture row spans exactly 18000000 milliseconds from start to end for the text bucket while every weekly span in it is exactly 604800000 milliseconds

Two type comments carry server semantics that no other file restates. The status comment in [`QuotaModelRemain`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/types/api.ts#L363-L365) maps 1 to normal, 2 to exhausted, and 3 to unlimited. The boost comment in the same type at [`api.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/types/api.ts#L369-L372) says the server returns a base weekly remaining percent plus a separate factor, and the rendered weekly value multiplies the base by `weekly_boost_permille` over 1000

## How the MiniMax client separates the interval window from the weekly window

Nothing in the client computes a 5 hour window, and nothing branches on a window lasting 5 hours. [`renderQuotaTable`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/output/quota-table.ts#L208-L243) renders two fixed metrics per row in API order. The first metric, labelled Left in English, always reads `current_interval_usage_count`, `current_interval_total_count`, and `current_interval_remaining_percent`. The second metric, labelled Wk left, always reads the three `current_weekly_` counterparts plus `weekly_boost_permille` and an unlimited flag from `current_weekly_status`. The weekly header range separately formats `weekly_start_time` and `weekly_end_time` from the first row only, at [`quota-table.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/output/quota-table.ts#L260-L262)

The only place a 5h label can appear is a derived tag next to the reset countdown. The tag is `formatWindow(m.end_time - m.start_time)` at [`quota-table.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/output/quota-table.ts#L238-L241), and [`formatWindow`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/output/quota-table.ts#L60-L69) renders an exact week multiple as weeks, an exact day multiple as days, anything of an hour or more as rounded hours, and anything shorter as rounded minutes. A bucket whose bounds span 5 hours therefore shows 5h, a daily bucket shows 1d, and a 2 hour bucket shows 2h, with the coding plan test rows asserting the 2h and 1d forms in [`quota-table.test.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/test/output/quota-table.test.ts#L198-L223). The countdown beside that tag always formats the interval `remains_time` and never `weekly_remains_time`, so the weekly reset instant reaches the table only through the header date range

The quiet output path is narrower still. With quiet set, `quota show` prints one tab separated interval line per model and never prints a weekly line, in [`show.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/commands/quota/show.ts#L48-L68). JSON output skips every interpretation and prints the raw response object unchanged, at [`show.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/commands/quota/show.ts#L43-L46)

Three status corner cases sit on top of the two window columns. A weekly metric renders as unlimited when `current_weekly_status` is 3, through [`isUnweekly`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/output/quota-table.ts#L97-L101). A row renders as not in plan when both totals are 0 and both statuses are 3, because [`isUnavailablePlan`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/output/quota-table.ts#L103-L111) treats that combination as a model with no bucket in the current plan rather than an unlimited model. No equivalent unlimited branch exists for the interval metric in this file, since the interval call to `renderMetric` passes no boost and no unlimited flag

## Which MiniMax model_name values appear

No code in the pinned tree dispatches on `model_name`, filters it, or groups by it. The single name aware helper is [`displayModelName`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/output/quota-table.ts#L40-L48), which only renames `general` and `video` into Chinese labels when the region is `cn`. Every other read renders `m.model_name` verbatim or prints it verbatim in quiet output, so the set of bucket names is defined by the server answer and observed only through fixtures and tests

The shipped fixture holds three buckets for one plan. `MiniMax-M*` carries a 5 hour interval span and a weekly total of 0, while `speech-hd` and `image-01` carry daily interval spans with positive weekly totals, in [`quota-response.json`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/test/fixtures/quota-response.json#L6-L47). Test data adds `MiniMax-M2` as the default table row and `MiniMax-M3` as the SDK quota row, plus a coding plan pair named `general` and `video` where `general` carries zero totals with server percents of 94 and 98 and a 2 hour interval span, in [`quota-table.test.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/test/output/quota-table.test.ts#L40-L73) and [`quota.test.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/test/sdk/quota.test.ts#L12-L29)

Read together, the coding or text allowance therefore arrives under `general` in the coding plan shaped answers and under a `MiniMax-M` family name such as `MiniMax-M*`, `MiniMax-M2`, or `MiniMax-M3` in the other answers, while `speech-hd` is the speech bucket, `image-01` is the image bucket, and `video` is the video bucket. That mapping is an observation over fixtures and tests rather than a rule the client enforces, so the only proven client contract is the `general` and `video` rename pair plus verbatim passthrough for every other string

## How the MiniMax client computes a remaining percent

Two separate computations touch a percent, and they answer different questions. [`resolveQuotaCounts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/utils/quota.ts#L18-L51) in `src/utils/quota.ts` decides what a reported `*_usage_count` means. Its own comment states that older responses use those fields as remaining counts while newer responses may use them as consumed counts, in [`quota.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/utils/quota.ts#L9-L17). When a finite server remaining percent is present, the function computes a percent both ways, as `reportedCount / total * 100` and as `(total - reportedCount) / total * 100`, picks the reading closer to the server percent, and returns undefined when even the closer reading sits more than the tolerance of 1 percentage point away from it. Without a server percent it keeps the legacy reading where the reported count is the remaining count. It also returns undefined for non finite inputs, a total at or below 0, or a reported count outside the range from 0 to the total

The displayed percent itself comes from [`remainingPct`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/output/quota-table.ts#L117-L133) in `src/output/quota-table.ts`. When a server percent exists it wins outright, multiplied by a boost factor of `weekly_boost_permille` over 1000 with a default factor of 1 when the boost is absent. Only when no server percent exists does the client derive one, as `remaining / total * 100` times the same factor, or 0 when the total is not positive. Either way the result is rounded and clamped into the range from 0 to a display ceiling of 200, at [`quota-table.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/output/quota-table.ts#L92-L95)

One wiring detail joins those two computations inside [`renderMetric`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/output/quota-table.ts#L154-L182). The bar percent is computed from the raw reported count, while the printed `remaining / total` pair comes from `resolveQuotaCounts`, and the percent text is shown beside the bar only when count resolution returned undefined. So a reconciled row shows counts, an unreconciled row falls back to the authoritative server percent alone, and the fallback percent when no server percent exists treats the raw reported count as remaining, which matches the legacy reading in `resolveQuotaCounts`

## MiniMax error handling for failed quota calls

The quota path has no retry, no fallback to the other usage endpoint, and no partial rendering. [`QuotaSDK.info`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/sdk/quota/index.ts#L18-L29) and the `quota show` command in [`show.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/commands/quota/show.ts#L20-L41) both let a rejection propagate. A non 2xx answer becomes a thrown `CLIError` from `mapApiError` inside [`request`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/client/http.ts#L166-L170), with the JSON body parsed when possible and an empty body assumed when it is not JSON. A 2xx answer with a non JSON body becomes a general `CLIError` about a non JSON response, and a 2xx answer whose `base_resp.status_code` is present and non zero becomes `mapApiError` called with a synthetic status of 200, both in [`requestJson`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/client/http.ts#L175-L193)

What the user sees then depends on the surface. The SDK base class only forwards to the same HTTP layer, in [`client.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/sdk/client.ts#L29-L35), so an SDK caller receives that `CLIError` as a rejection. The CLI routes a `CLIError` through [`handleError`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/errors/handler.ts#L5-L19), which prints the message and hint or a JSON error object and exits with the error exit code. The one caller that softens a quota failure is `auth status` in text mode, which catches the fetch error, prints `Quota fetch failed` with the message, and still reports the authentication state, in [`status.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/commands/auth/status.ts#L63-L71)

## MiniMax chat and text error envelope

Chat in this client is the Anthropic Messages shape rather than an OpenAI chat completions shape. [`chatEndpoint`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/client/endpoints.ts#L1-L3) builds `{baseUrl}/anthropic/v1/messages`, the request and response types are the Messages style [`ChatRequest`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/types/api.ts#L20-L43) with `model`, `messages`, and `max_tokens`, and no source file calls a `chat/completions` path. Both the CLI command in [`chat.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/commands/text/chat.ts#L244-L253) and the SDK in [`text/index.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/sdk/text/index.ts#L34-L48) post to that URL with `authStyle` set to `x-api-key`, so chat sends an `x-api-key` header while the quota and balance reads above send a bearer token. The header switch itself is the branch in [`request`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/client/http.ts#L111-L119)

Errors from that POST surface through the exact same two functions as quota, because the SDK `Client` base only delegates to `request` and `requestJson` in [`client.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/sdk/client.ts#L29-L35). A non streaming chat call goes through `requestJson`, so it can fail as a non 2xx status, as a non JSON 2xx body, or as a 2xx body whose `base_resp.status_code` is non zero. A streaming chat call goes through `request`, so an upstream HTTP failure still throws before any event stream starts, at [`http.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/client/http.ts#L166-L170). Malformed stream chunks after a successful start are a different local path, where the CLI warns and keeps partial output in [`chat.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/commands/text/chat.ts#L275-L301)

The body shape the client reads is declared once as [`ApiErrorBody`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/errors/api.ts#L4-L15) in `src/errors/api.ts`. It allows a classic MiniMax envelope with `base_resp` holding a numeric `status_code` and a string `status_msg`, and it also allows an OpenAI or Anthropic style envelope with `error` holding a string `message`, a string `type`, a numeric `code`, and an `http_code` as string or number. [`mapApiError`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/errors/api.ts#L33-L41) then folds both envelopes into three locals in a fixed order. The message prefers `base_resp.status_msg`, then `error.message`, then a synthetic `HTTP {status}` string. The code prefers `base_resp.status_code`, then `error.code`, using a truthy fallback so a `status_code` of 0 falls through to `error.code`. The type reads only `error.type`. The declared `error.http_code` field is never read anywhere in `src`, since a search finds it only in that type declaration, so the status that drives classification is always the fetch status passed in by the caller or the synthetic 200 from `requestJson`

A parenthesized business code inside the message is not a parsed field either. Messages such as `insufficient balance (1008)` arrive in tests under `error.message` alongside `error.type` and `error.http_code`, in [`api.test.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/test/errors/api.test.ts#L22-L34), and the mapper classifies that case from the 402 status and the `insufficient_balance_error` type while keeping the whole message text verbatim. The single place a numeric token inside a message matters is the video v2 content filter probe in [`mapApiError`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/errors/api.ts#L94-L97), which requires status 422 and type `unprocessable_entity_error` and then accepts either a sensitive content phrase or a standalone 1026 token in the message

Classification is status first and business code second, and the order is observable. Statuses 401 and 403 become an auth error, status 429 becomes a quota error with the folded message appended, status 402 or type `insufficient_balance_error` becomes a quota error, and statuses 408 and 504 become a timeout, all in [`mapApiError`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/errors/api.ts#L42-L72). Two speech to text endpoint cases follow for 422 and 413. Only after those branches does the mapper read the folded code, mapping 1002, 1039, and 1026 to a content filter error at [`api.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/errors/api.ts#L100-L109), mapping 1028 and 1030 to a quota error at [`api.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/errors/api.ts#L112-L119), mapping 2061 to a model not on the plan quota error at [`api.ts`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/errors/api.ts#L122-L129), and mapping 1027 or an output sensitive message to a content filter error right after it. Anything else becomes a general error carrying the folded message and the HTTP status. The documented MiniMax usage codes 2056, 2062, and 2067 have no branch in this file or anywhere else in `src`, so a chat failure carrying one of those codes is classified by its HTTP status alone, or as a general error when it arrives on a 200 `base_resp` body

The exit code vocabulary behind those branches is small and stable. [`ExitCode`](https://github.com/MiniMax-AI/cli/blob/38aba5f26173dd1065b115b221d79c9ddd87c6bb/src/errors/codes.ts#L1-L9) in `src/errors/codes.ts` assigns quota the value 4, auth the value 3, timeout the value 5, and content filter the value 10, and `mapApiError` returns a `CLIError` carrying one of those values plus an optional hint

## How the Kimi Code client sends chat requests

Two different upstreams share the provider type named `kimi`, and the base URL decides which one a chat request reaches. The provider default baked into the protocol layer is the paid Moonshot API at `https://api.moonshot.ai/v1`, declared as [`KIMI_DEFAULT_BASE_URL`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/builtin/provider/kimi/protocol.ts#L31) and consumed as the endpoint default in [`index.ts`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/builtin/provider/kimi/index.ts#L15-L23). The managed Kimi Code subscription upstream instead defaults to `https://api.kimi.com/coding/v1` with a global sibling at `https://api.kimi.ai/coding/v1`, in [`managed-usage.ts`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/oauth/src/managed-usage.ts#L8-L19) inside the OAuth package, where an environment `KIMI_CODE_BASE_URL` wins over the default. Login provisioning writes the managed provider with type `kimi` and that managed base URL, in [`authService.ts`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/app/auth/authService.ts#L563-L576), so later connection resolution prefers the configured model or provider base URL over the protocol default through [`resolveModelConnection`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm-requester/connection.ts#L23-L43)

Which wire protocol carries a given managed model is declared by the upstream models answer rather than hardcoded. [`parseModelProtocol`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/oauth/src/managed-kimi-code.ts#L16-L22) maps a model `protocol` field of `anthropic` to anthropic and `response` to `openai_responses`, and leaves everything else undefined. [`toManagedModelAlias`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/oauth/src/managed-kimi-code.ts#L594-L626) then marks anthropic models for the beta Messages API, with a comment stating the endpoint is served behind `/v1/messages?beta=true`. The agent side registers provider type `kimi` three times, once per base protocol `openai`, `anthropic`, and `openai_responses`, each with its matching requester and the same quota error classifier, in [`provider-definition.ts`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/llm-adapter/provider/provider-definition.ts#L196-L228). A model with no declared protocol resolves through the provider definition default base protocol, which is the OpenAI shaped path, through [`resolveModelProtocol`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/llm-adapter/model/model-auth.ts#L140-L161)

The actual send is delegated to the official SDKs, with local SDK retry disabled. The OpenAI shaped path constructs `new OpenAI` with the resolved apiKey, baseURL, default headers, a timeout aware fetch, and `maxRetries` of 0, then calls `client.chat.completions.create` with `stream` false for a plain request or `stream` true plus `include_usage` stream options for a streamed one, in [`openai/index.ts`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/builtin/protocol/openai/index.ts#L45-L82). The Anthropic shaped path constructs `new Anthropic` with the resolved apiKey, a null auth token, the resolved baseURL, and `maxRetries` of 0, then calls `client.messages.create` or `client.beta.messages.create` when the beta API flag is set, in [`anthropic/index.ts`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/builtin/protocol/anthropic/index.ts#L67-L120). The responses shaped path reuses the OpenAI error decoder, since [`openai-responses/index.ts`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/builtin/protocol/openai-responses/index.ts#L1-L15) imports `decodeError` from the OpenAI protocol folder. Streaming is the default at the registry seam, because [`ProtocolAdapterRegistry.request`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/llm-adapter/protocol/protocolAdapterRegistry.ts#L239-L250) fills `stream` with true when the caller left it unset

Kimi specific request shaping happens as protocol overrides over those base protocols. [`kimiOpenAIProtocol`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/builtin/provider/kimi/protocol.ts#L154-L190) renames the output cap to `max_completion_tokens`, converts tools whose names start with `$` into builtin function tools, emits a Kimi `thinking` object, hoists a per choice usage object onto the chunk, and reads the request id from an `x-trace-id` header. [`kimiAnthropicProtocol`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/builtin/provider/kimi/protocol.ts#L192-L207) keeps the same request id header and error wrapping over the Anthropic base. Credentials reach those clients as a plain apiKey string, since [`resolveEndpoint`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/endpoint.ts#L29-L37) resolves an endpoint credential into a baseUrl, an apiKey, merged headers, and a fetch implementation, so an OAuth access token travels as that apiKey and the chosen SDK decides the concrete auth header

## How the Kimi Code client parses chat error responses

Following the error tokens back to types matters here, because nothing in the chat path parses a raw HTTP JSON body directly. An upstream HTTP failure first becomes an SDK API error object from the `openai` or `@anthropic-ai/sdk` package, and only that object enters a `decodeError` function. The local normalized target type is [`LlmRemoteErrorMessage`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/response.ts#L27-L83) in `src/human/llm/response.ts`, whose status shaped kinds carry a message plus a status code, a request id, retry after milliseconds, response headers, and a retryable flag. Every claim below about `error.message`, `error.type`, or `error.code` therefore names a field on an SDK error object or on the body object the SDK already extracted from the response

The Kimi specific layer runs ahead of the base decoders for non streaming failures. [`withKimiErrors`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/builtin/provider/kimi/protocol.ts#L138-L145) wraps all three Kimi protocols so a source of `stream` goes straight to the base decoder, while any other source tries [`classifyKimiQuotaError`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/builtin/provider/kimi/errors.ts#L29-L56) first. The registry applies the same ordering at its seam in [`protocolAdapterRegistry.ts`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/llm-adapter/protocol/protocolAdapterRegistry.ts#L242-L247), where a provider `classifyError` hook wins over the protocol base decoder outside streaming

That classifier is deliberately narrow and entirely structured. [`collectErrorCodes`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/builtin/provider/kimi/errors.ts#L16-L27) walks up to three levels following each `error` object property and collects every string `code` and every string `type` it finds. A hit needs one of those strings to equal the single set member `exceeded_current_quota_error` declared at [`errors.ts`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/builtin/provider/kimi/errors.ts#L4), and it needs the top level `status` field to be 429 or absent. On a hit it returns kind `quota_exhausted` with `retryable` false, a message read from `error.error.message` and then from `error.error.error.message` for the Anthropic nesting, a request id from the top level `requestID` field, and retry after plus headers read from the top level `headers` field. Its tests pin both nesting depths and pin the negative case by name, since [`errors.test.ts`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/test/llm/errors.test.ts#L361-L421) asserts that a 429 whose message wording says insufficient balance classifies as nothing when no structured code is present, and that a non 429 status ignores the quota code entirely

Under that layer, the exact JSON shapes differ per base protocol. The OpenAI decoder in [`decodeError`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/builtin/protocol/openai/decode.ts#L387-L460) accepts only an SDK API error instance and reads its `error` field as a body object with optional `code`, `message`, and `type`, so the HTTP body it assumes is an object with an `error` object carrying those three optional fields. Its message comes from that body `error.message` or an empty string, its code prefers the SDK lifted `error.code` and then the body code, its type prefers the SDK lifted `error.type` and then the body type, and its status, request id, retry after, and headers come from the SDK error `status`, `requestID`, and `headers` fields. The Anthropic decoder in [`decodeError`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/builtin/protocol/anthropic/decode.ts#L230-L295) assumes one more level of nesting, reading the SDK `error` field as a whole body with an inner `error` object carrying `type` and `message`, so its message comes from `error.error.message` and its type from `error.error.type` with a fallback to the SDK lifted `error.type`. No `code` field is read on the Anthropic path

Code sets then decide the kind before raw status gets a say. On the OpenAI path a status of 429 or an absent status combined with `insufficient_quota` or `exceeded_current_quota_error` in any of the lifted code, lifted type, body code, or body type yields `quota_exhausted` with `retryable` false, through [`isOpenAIInsufficientQuotaCode`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/builtin/protocol/openai/decode.ts#L359-L386). A code or type of `overloaded_error` or `engine_overloaded_error` yields `overloaded` with `retryable` true at any status, a `context_length_exceeded` code yields `context_overflow` with `retryable` false, and the rate codes `rate_limit_exceeded`, `rate_limit_reached_error`, and `rate_limit_error` are declared in [`isOpenAIRateLimitErrorCode`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/builtin/protocol/openai/decode.ts#L367-L378) but consulted only when no HTTP status is present, as on a streamed error body. The Anthropic path checks the same quota, overload, and rate strings against its single type value and likewise yields `quota_exhausted` as non retryable and `overloaded` and `rate_limit` as retryable, at [`decode.ts`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/builtin/protocol/anthropic/decode.ts#L250-L265)

Whatever survives code classification falls into status rules shared by both paths. [`toLlmStatusErrorMessage`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/protocol/rules/status.ts#L167-L196) maps any 429 to `rate_limit` outright, then tests narrower message patterns for context overflow at statuses 400, 413, and 422, for request too large at 413, for provider overload only at status 529 or at 500 and 503 whose message matches an overload pattern, and for request structure and image format problems, leaving a generic `status` kind otherwise. Retryability for that generic outcome comes from [`isTransientHttpStatus`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/protocol/rules/status.ts#L124-L140), which covers 408, 409, 429, 500, 502, 503, 504, and 529. Retry timing can still come from the response even when the body carried nothing useful, since [`parseRetryAfterMs`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/protocol/kit/http.ts#L26-L37) reads only a delta seconds `retry-after` header and converts it to milliseconds. Streamed failures add one more distinction, because both base decoders blank the status code when the source is a stream and instead map a business code of 429 to `rate_limit`, 529 to `overloaded`, and 413 to `request_too_large` through [`toLlmStreamErrorMessage`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/protocol/rules/status.ts#L142-L165)

Against the documented Kimi Code 429 catalogue, the honest finding is an absence. A search of the pinned tree finds no quota window message text and no concurrency message classifier in the LLM error path, and the only message patterns anywhere near that path are generic ones, namely the overload pattern in [`status.ts`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/protocol/rules/status.ts#L27) and, one layer up where normalized errors become public API errors, the rate limit wording patterns covering too many requests and rate limit phrasing in [`errors.ts`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/llm-adapter/contract/errors.ts#L343-L353). So a documented 5 hour, weekly, or monthly quota rejection becomes `quota_exhausted` and stops retrying only when the upstream also attaches the structured `exceeded_current_quota_error` code or one of the base quota codes. A documented concurrent request rejection and a documented too many requests rejection both become plain retryable `rate_limit` by status. A documented overloaded engine rejection becomes `overloaded` only when it carries an overload code or type, arrives as a 529, or arrives as a 500 or 503 with overload wording, and the same rejection sent as a plain 429 would land as `rate_limit` instead

Retry behavior then follows the normalized flag rather than any Kimi specific table. Both SDK clients disable their own retries with `maxRetries` of 0, so the only retry loop is the local policy in [`retry.ts`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/policy/retry.ts#L33-L55). There an error is retryable when its `retryable` flag is true and it is neither a syntax nor an abort error, [`shouldRetry`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/policy/retry.ts#L47-L55) caps attempts at a default of 10 from [`DEFAULT_MAX_RETRY_ATTEMPTS`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/agent-core-v2/src/human/llm/policy/retry.ts#L3), and delays grow from 500 milliseconds by doubling with jitter up to 32 seconds unless a `retry-after` value was captured. The practical split for Kimi Code is therefore stark. A structured quota code ends the request with no retry, while every other documented 429 flavor retries under the generic rate limit budget

One adjacent managed surface belongs in this note because it changes what a quota error means operationally. The managed client can actively read usage from `GET {base}/usages`, built by [`kimiCodeUsageUrl`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/oauth/src/managed-usage.ts#L21-L23), and [`parseQuotaUsages`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/oauth/src/managed-usage.ts#L118-L137) reads entries named `limit_5h`, `limit_7d`, `limit_month_total`, and `limit_month_code`, each as a `used_ratio` number or numeric string with an optional `reset_time` string. That read uses a bearer token and a hand rolled fetch in [`fetchManagedUsage`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/oauth/src/managed-usage.ts#L218-L256), and its failure message is extracted from a plain JSON error body by [`extractApiErrorMessage`](https://github.com/MoonshotAI/kimi-code/blob/df90d90ec0714db23dcc830acd2db6232f5c7426/packages/oauth/src/api-error.ts#L6-L42), which tries top level `error_description`, `message`, and `detail`, then a string `error`, then nested `error` fields named `message`, `error_description`, `detail`, `code`, and `type`. That OAuth package helper is a separate error reader from the chat decoders above and the two should not be merged when porting either behavior
