# CLIProxyAPI quota signals and what OLP could adopt

Status: research note, fetched 2026-11-05. Facts below come from primary sources only, meaning the CLIProxyAPI source tree, vendor documentation, and vendor client source. Each claim names its source so a reader can tell stale from broken

Pinned sources are [CLIProxyAPI at 585f97d](https://github.com/router-for-me/CLIProxyAPI/tree/585f97deac9aa57c700301221fb1a7085e1827cc) and [the official Codex client at c0100ad](https://github.com/openai/codex/tree/c0100ad4ecd2251c2b48b68534db08afac78c606). Vendor documentation was fetched live on the date above, so plan numbers in it can move without any code change here

Two evidence labels run through the vendor section. Proven means a vendor document or vendor client source states the signal, so OLP could build on it and cite it. Heuristic means the signal exists only as parsing or classification logic inside CLIProxyAPI, where it encodes observed upstream behavior that no vendor page fetched here promises

The short version is that CLIProxyAPI does not order accounts by remaining allowance at all. It observes quota passively for display, it cools an account down after a failure, and it spreads new work with round robin, weighted round robin, or fill first inside the highest priority tier. The reset aware part is the wait between retry rounds, which targets the earliest recovery deadline. Anything smarter, such as preferring the account with the most remaining percent or the soonest useful reset, would be new work for OLP rather than a port

## How CLIProxyAPI selects an account

Selection starts from eligibility, not from quota. A credential is blocked for a model when it is disabled, when its access token is expired, when a credential wide quota deadline is still in the future, or when the per model state is unavailable or quota exceeded with a recovery time still ahead. The check lives in [`isAuthBlockedForModelForRequest`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/selector.go#L842) and [`availabilityBlock`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/selector.go#L904) in `sdk/cliproxy/auth/selector.go`

Eligible credentials are then narrowed to the single highest priority tier. Priority comes from the credential attribute named `priority`, and only that tier is handed to the strategy, sorted by credential ID. The narrowing lives in [`collectAvailableByPriorityForRequest`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/selector.go#L474) and [`availableAuthsFromPriorityBuckets`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/selector.go#L561)

Three built in strategies then pick inside that tier. Round robin is the default and resumes after the last picked ID per provider and model key, in [`RoundRobinSelector.Pick`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/selector.go#L623). Weighted round robin is the smooth variant where each pick adds its weight to every candidate and subtracts the total from the winner, in [`WeightedRoundRobinSelector.Pick`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/selector.go#L682) and `pickSmoothWeightedAuth` in the same file. Fill first always takes the first available credential, in [`FillFirstSelector.Pick`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/selector.go#L821). The configuration surface names the same three strategies and states that weighted round robin uses an integer weight per credential with a default of 1, a maximum of 1,000,000, and exclusion for non positive weights, in the [example configuration routing block](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/config.example.yaml#L169-L242)

A scheduler fast path mirrors those semantics without scanning every credential per request. Per provider and model shards keep ready and blocked views per priority, expired blocks are promoted back to ready on read, and the same three pick shapes run inside the shard. The entry points are [`authScheduler.pickSingleWithStrategy`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/scheduler.go#L401) and [`modelScheduler.pickReadyLocked`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/scheduler.go#L1324) in `sdk/cliproxy/auth/scheduler.go`

Session affinity is an optional wrapper around any of the strategies. When enabled, an established session binding outranks priority and keeps its credential while that credential stays available, with a one hour default binding lifetime. The wrapper is [`SessionAffinitySelector.Pick`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/selector.go#L1123), and the configuration documents the `session-affinity-rebind-on` choice between rebinding on any credential failure and rebinding only on quota or auth class failures while transient failures borrow another credential for one request, in the [example configuration routing block](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/config.example.yaml#L169-L242)

Two narrower preferences sit inside selection and neither reads quota. Codex websocket requests prefer websocket enabled credentials when any exist, in `preferCodexWebsocketAuths` in [`selector.go`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/selector.go#L446). A plugin scheduler can replace the built in pick entirely through `pickViaPluginScheduler` in [`conductor_selection.go`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_selection.go#L995), which is the only seam where an operator supplied ordering could consume quota data today

When every candidate for a model is in cooldown, selection returns a synthetic 429 whose `Retry-After` header is the earliest recovery deadline among the blocked credentials. That behavior lives in `modelCooldownError` in [`selector.go`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/selector.go#L350-L364)

## How CLIProxyAPI reads quota and allowance

The core state is deliberately split in two. [`QuotaState`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/types.go#L340) in `sdk/cliproxy/auth/types.go` carries scheduling fields, namely `Exceeded`, `Reason`, `NextRecoverAt`, and `BackoffLevel`, plus an observation snapshot made of `ObservedAt` and a bounded `Signals` map. Per model state in [`ModelState`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/types.go#L373) carries the same pair per model, so a model scoped rejection does not have to block the whole credential

Passive observation is the main quota reader and it is display only. [`QuotaState.ObserveResponseHeadersForProvider`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/quota_signals.go#L37) replaces the snapshot with the signals from one upstream response, never merges across responses, and its own comment states that cooldown and scheduling fields are never read or written there. Only three providers participate, namely `claude`, `codex`, and `devin`, per [`ProviderSupportsQuotaObservation`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/quota_signals.go#L17)

The header allowlist is explicit. For Codex it keeps `Retry-After`, `x-codex-plan-type`, `x-codex-active-limit`, the `x-codex-credits-` family, and any `x-codex-` name containing one of `-allowed`, `-limit-reached`, `-limit-name`, `-used-percent`, `-window-minutes`, `-reset-after-seconds`, `-reset-at`, or `-over-secondary-limit-percent`. For Claude it keeps `Retry-After` and the `anthropic-ratelimit-unified-` family. The rules live in [`isQuotaSignalHeaderForProvider`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/quota_signals.go#L170), snapshots are capped at 64 headers with values capped at 512 bytes, and retention ranking keeps credential level watermarks ahead of additional limit namespaces when truncating, in [`collectQuotaSignals`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/quota_signals.go#L92)

Codex websocket quota events are normalized into the same header shape. [`ParseCodexQuotaEventHeaders`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/internal/runtime/executor/helps/codex_quota.go#L29) in `internal/runtime/executor/helps/codex_quota.go` reads `codex.rate_limits` events with primary and secondary windows carrying `used_percent`, `window_minutes`, `reset_after_seconds`, and `reset_at`, plus additional rate limits, code review limits, credits, plan type, and the active metered limit name. Its header comment notes that the `/wham/usage` probe exposes the equivalent data as an array, but no code in the pinned tree calls that endpoint for Codex, since a search for `wham/usage` finds only that comment

The one built in active quota fetch is for Devin, which is outside the OLP adapter set. [`DevinAuthService.FetchUserStatus`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/internal/auth/devin/user_status.go#L335) parses daily and weekly remaining percents with reset timestamps into the same `Signals` map

Active fetching for everything else is delegated to plugins or to an operator written probe. The plugin contract is [`QuotaProvider`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/pluginapi/types.go#L1738) in `sdk/pluginapi/types.go`, with a normalized response made of groups and [`QuotaBucket`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/pluginapi/types.go#L1839) values carrying a window name, a remaining fraction, and a reset time. The management handler [`FetchCredentialQuota`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/internal/api/handlers/management/plugin_quota.go#L61) calls the plugin when one is registered and otherwise falls back to a declarative `quota_probe` stored in credential metadata, which [`executeQuotaProbe`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/internal/api/handlers/management/plugin_quota.go#L384) runs as an operator configured HTTP request with a `$TOKEN$` placeholder and an optional response mapping. No quota provider plugin for Codex, GLM, MiniMax, Kimi, Qwen, or OpenCode Go ships in the pinned tree

What the operator can see is the passive snapshot only. The management auth file listing exposes `quota` and `model_quotas` observation payloads and deliberately strips the cooldown fields from them, in `quotaObservationPayload` in [`auth_files.go`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/internal/api/handlers/management/auth_files.go#L874-L912). A manual reset endpoint clears routing cooldown state without touching the upstream allowance, through [`Manager.ResetQuota`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_cooldown.go#L540)

## How CLIProxyAPI cools an account down

Cooldown is written after the fact by [`Manager.MarkResult`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_cooldown.go#L889) in `sdk/cliproxy/auth/conductor_cooldown.go`. Every execution reports a result with its provider, model, error, an optional retry hint extracted by [`retryAfterFromError`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_cooldown.go#L2444), and a credential scope flag when the executor vouches that the failure covers the whole credential rather than one model

For a 429 the deadline prefers the upstream hint. When a hint exists it is used as the cooldown with a floor of 10 seconds, and when no hint exists the code falls back to an exponential ladder that starts at 1 second, doubles per backoff level, and caps at 30 minutes. The ladder is [`nextQuotaCooldown`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_cooldown.go#L3152) with constants in [`conductor_refresh.go`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_refresh.go#L37-L40), and [`quotaCooldownAfterFailure`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_cooldown.go#L3139) makes a burst of in flight failures inside one open window reuse that window instead of escalating the ladder more than once

Other statuses get fixed or configurable treatment in the same switch. Auth and payment class failures at 401, 402, and 403 cool for 30 minutes, a 404 cools for 12 hours unless a hint says otherwise, and transient statuses at 408, 500, 502, 503, 504, and 520 through 526 cool for the hint when present and otherwise for one minute by default. The transient default is the `transientErrorCooldown` constant plus the `transient-error-cooldown-seconds` setting where 0 keeps the legacy one minute and a negative value disables transient cooldowns, per the [example configuration cooldown block](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/config.example.yaml#L231-L242)

Credential scope decides how wide a 429 lands. A credential scoped failure raises the auth level `credential_quota` deadline and propagates it over every model state while preserving each model own earlier block in a shadow layer, while an ordinary model scoped failure cools only the reporting model. That propagation and shadow handling sits inside `MarkResult` in [`conductor_cooldown.go`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_cooldown.go#L1119-L1166)

Cooldowns only ever move later while live. A new failure whose computed deadline is earlier than a still live deadline keeps the later one, and a success that was dispatched before a cooldown was recorded cannot clear it because successes are fenced by an execution sequence watermark. Both rules sit in `MarkResult` and its helpers in [`conductor_cooldown.go`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_cooldown.go#L889)

Cooldown state is memory only by default and can be persisted next to the auth files as `.cds` records when `save-cooldown-status` is enabled, and cooling can be disabled globally, per provider, or per credential through `disable-cooling`. Both switches are documented in the [example configuration cooldown block](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/config.example.yaml#L231-L242)

Where the hint comes from depends on the executor, and this is where vendor specific knowledge concentrates. For Codex, [`parseCodexRetryAfter`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/internal/runtime/executor/codex_executor_terminal.go#L531) reads `resets_at` and then `resets_in_seconds` from a 429 body whose error type is `usage_limit_reached`, and [`isCodexUsageLimitError`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/internal/runtime/executor/codex_executor_terminal.go#L514) marks exactly that type as credential scoped quota exhaustion. Transient Codex capacity rejections are classified the other way, as model scoped and never quota, through the `turn_rate_limit_exceeded` and model at capacity checks in the same file. For Claude, [`ParseClaudeRateLimitReset`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/internal/runtime/executor/helps/claude_ratelimit.go#L231) collects `Retry-After` plus the unified 5 hour, 7 day, and combined reset headers for whichever windows report `rejected`, takes the latest deadline, and adds a random grace of 1 to 30 seconds. For generic OpenAI compatible upstreams, which is how GLM, MiniMax, Qwen, and OpenCode Go style endpoints are reached in this codebase, [`openAICompatRetryAfter`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/internal/runtime/executor/openai_compat_executor.go#L1351) honors the standard `Retry-After` header parsed by [`parseRetryAfterHeader`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/internal/runtime/executor/openai_compat_executor.go#L1323), with one narrow fallback that invents a one minute hint for bodies that clearly describe a per minute token limit

## Reset aware ordering, or the lack of it

No built in selector or scheduler path reads `QuotaState.Signals`, a used percent, a remaining fraction, or a reset time to order ready credentials. A search across `sdk/cliproxy/auth/selector.go` and `sdk/cliproxy/auth/scheduler.go` finds no reference to the observation snapshot, and the observation writer itself states that scheduling fields are never touched there, in [`quota_signals.go`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/quota_signals.go#L37-L56). Ordering inputs are exactly priority, the configured weight, credential ID order, session binding, and the Codex websocket preference

Reset times influence only two things. They set the cooldown deadline that removes a credential from the ready set, and they set the wait before a credential retry round, which is covered next. Even the Claude utilization headers are only classified, never ranked, since [`ClaudeHeadersIndicateUnifiedRateLimitRejection`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/internal/runtime/executor/helps/claude_ratelimit.go#L29) distinguishes a shared window rejection from an overage only rejection so the cooldown lands at the right scope

The practical read for OLP is that a least used first or soonest reset first ordering is not hiding in this codebase. The closest existing shapes are fill first, which drains one account before touching the next and so keeps whole accounts in reserve, and weighted round robin, which can encode a static operator guess about relative plan size through the weight attribute

## How CLIProxyAPI fails over and retries

Failover inside one request happens in the execution loop. [`Manager.Execute`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_execution.go#L127) runs rounds, and each round calls [`executeMixedOnce`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_execution.go#L517), which keeps picking the next untried credential, executes, records the result, and continues to another credential on failure until one succeeds or the round runs out of candidates. A 401 first tries one token refresh and a single re execution on the same credential before failing over, inside `executeMixedOnce` in [`conductor_execution.go`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_execution.go#L517)

A second round is gated on status and on per credential retry budgets. Only 403, 408, 429, 500, 502, 503, and 504, plus transient transport failures, can open another round, per [`isCredentialRetryRoundStatus`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_selection.go#L1580). The global `request-retry` default is 3 additional rounds, a per credential or per provider override wins, an explicit 0 admits only the first round, and round r only admits credentials whose effective retry limit is at least r. The settings are documented in the [example configuration retry block](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/config.example.yaml#L204-L229) and enforced through `effectiveRequestRetryLimit` and `requestRetryRoundExclusions` in [`conductor_selection.go`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_selection.go#L1157-L1187)

The wait between rounds is the one genuinely reset aware behavior. [`shouldRetryAfterErrorWithAttempted`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_selection.go#L1465) asks [`closestCooldownWaitWithAttemptedForRequest`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_selection.go#L1294) for the smallest remaining cooldown among credentials that are still retry eligible for the next round, so the request sleeps until the first useful account recovers rather than for a fixed backoff. A credential that already failed with 429 in the round that just ended gets at least the 10 second floor so it cannot trigger an immediate zero wait round. The wait is capped by `max-retry-interval`, which defaults to 30 seconds and where a non positive value means never wait, and [`waitForCooldown`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_selection.go#L1628) adds jitter of up to 2 seconds through `jitteredCooldownWait` so concurrent waiters do not wake in lockstep. A per round cap on distinct credentials also exists as `max-retry-credentials`, where 0 tries every available credential, per the [example configuration retry block](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/config.example.yaml#L204-L229)

Streaming failover is bounded by first output. [`readStreamBootstrap`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_stream.go#L93) buffers the opening chunks so a bootstrap error can still fail over to another credential, and the configuration adds an optional `bootstrap-retries` count for retries before the first byte is sent, in the [example configuration streaming block](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/config.example.yaml#L265-L269). This is a weaker contract than the OLP code mode rule, where recovery needs proof that the request did not execute rather than merely proof that no byte reached the client, per the [OLP code mode guide](/home/ubuntu/code/olp/1/olp/docs/use/code-mode.md) and [ADR 0002 on state aware code account recovery](/home/ubuntu/code/olp/1/olp/docs/adr/0002-state-aware-code-account-recovery.md)

## Vendor quota and reset signals

The summary below separates a machine readable signal from a plan rule that a human can read in a console. A documented window helps explain a rejection, but it does not by itself tell OLP when this account resets or how much this account has left

| Adapter | Strongest primary source signal | Evidence |
|---|---|---|
| Codex | Passive window headers and events, plus an active usage read in the official client | Proven |
| GLM Coding Plan | Documented 429 business codes with a reset time inside some messages | Proven message, heuristic extraction |
| MiniMax M Plan | Documented usage API URL, with no response schema on the fetched page | Proven endpoint, unproven schema |
| Kimi Code | Documented quota windows and exact quota error messages, with no reset timestamp in those messages | Proven |
| Qwen Token Plan | Documented monthly Credits quota and an `insufficient_quota` 429 | Proven |
| OpenCode Go | Documented per model windows and a per response allowance charge | Proven |

The table is only a map. The source for each row is in its vendor section below, and the adoption section uses the narrower reading from those sections rather than the compressed row

### Codex and ChatGPT subscription

OpenAI documents the plan shape before any wire signal matters. The pricing page says estimates are shown per five hour period for Plus and Standard Business, says Pro plans currently have no five hour limit, says weekly limits may also apply, and points readers to the usage dashboard for current limits and reset times. It also says `/status` shows remaining limits during an active Codex CLI session. Source is [OpenAI Codex pricing](https://learn.chatgpt.com/docs/pricing)

## What OLP could adopt

OLP starts from a stricter position than CLIProxyAPI. A conversation tree pins one account per subscription family and per model, an unavailable pinned account does not trigger silent switching, and new conversation share can already be weighted per pool account. Sources are the [OLP code mode guide](../use/code-mode.md) and [the candidate choice in `code_mode.go`](../../internal/resources/code_mode.go#L536-L583)

OLP also already reads Codex allowance windows and uses exhausted windows as an availability gate, while OpenCode Go and the coding plans currently show no allowance and take health from response status plus a single valid `Retry-After` with a one minute fallback. Source is the [OLP code mode guide](../use/code-mode.md)

That means most useful adoption is not a selector port. It is a set of adapter observation contracts that feed the availability gate OLP already has, plus a new ordering rule for new roots only

| Area | Port the idea | New OLP work |
|---|---|---|
| Cooldown scope | Keep quota, rate, capacity, and concurrency as separate failure classes | Add adapter classifiers and per model or per limit health where the vendor signal proves that scope |
| Cooldown deadline | Prefer an upstream reset over a fallback and never shorten a live deadline | Parse only exact documented body fields or codes for each adapter |
| New root ordering | Use static pool weights today as the plan size share | Add fresh allowance bands ahead of the existing weighted score |
| Active quota read | Normalize a fetched answer into windowed allowance buckets | Add a non inference plugin capability, approved origins, schema fixtures, and failure isolation |
| All accounts busy | Report the earliest useful recovery time | Add that deadline to the existing unavailable refusal without changing pinned ownership |
| Failover | Classify a complete rejection before any replay decision | Prove nonexecution per adapter and keep the existing explicit recovery policy in charge |

### Shared changes worth doing once

The first shared change is a wider allowance vocabulary. The current window type only names `primary` and `secondary`, and its value is a percent pair, which fits Codex and does not honestly describe a GLM credit, a Qwen monthly Credit, or an OpenCode cent charge. Sources are [`AllowanceWindowNames`](../../internal/codemode/observations.go#L15-L19) and [`AllowanceWindow`](../../internal/codemode/observations.go#L131-L145)

A new observation should carry the limit family, a bounded window name such as `five_hour`, `weekly`, or `monthly`, the unit, a remaining or used value when the vendor actually reports one, the reset time when the vendor actually reports one, the observation time, and the evidence label. That is new domain and storage work, even where the normalized bucket shape follows the CLIProxyAPI plugin contract in [`QuotaBucket`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/pluginapi/types.go#L1839)

The second shared change is scope. An account wide monthly exhaustion, a model entitlement rejection, a short concurrency rejection, and an overloaded upstream should not all become the same account health state for the same duration. CLIProxyAPI keeps that split through credential scope and per model state in [`MarkResult`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_cooldown.go#L889), while OLP currently marks account health from status in [`code_attempt.go`](../../internal/gateway/code_attempt.go#L333-L354). The concept is a port, and the durable OLP implementation is new work

The third shared change is ordering for new roots only. A safe rule would put eligible accounts into coarse bands from fresh proven observations, with exhausted accounts already ineligible, known low accounts below unknown accounts, and unknown accounts below known healthy accounts. The existing deterministic weighted score would then choose inside the best band, which keeps concurrent first turns stable and avoids every new conversation herding onto the one account with the newest snapshot. This is new policy and selection work, not CLIProxyAPI behavior

Soonest reset should stay a secondary rule. It can break ties inside a low band when an operator wants to spend a short window before it expires, and it can set the recovery time on an unavailable refusal. It should not make the gateway sleep for a long reset, and it should never move an established pin. The bounded wait and earliest deadline ideas come from [`closestCooldownWaitWithAttemptedForRequest`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/sdk/cliproxy/auth/conductor_selection.go#L1294), while the pin boundary comes from the [OLP code mode guide](../use/code-mode.md)

### Codex

Keep the passive path OLP already has. The useful port is completeness of classification, where a documented `usage_limit_reached` stays a credential quota signal and a capacity rejection stays a shorter model scoped cooldown. The official client proves the quota error fields in [the 429 branch in `api_bridge.rs`](https://github.com/openai/codex/blob/c0100ad4ecd2251c2b48b68534db08afac78c606/codex-rs/codex-api/src/api_bridge.rs#L208-L240), while the capacity split remains a CLIProxyAPI heuristic in [`isCodexTransientCapacityError`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/internal/runtime/executor/codex_executor_terminal.go#L470-L512)

New work would be an operator triggered or worker run read of the official client usage endpoint. That read is not synthetic inference, but it is a new credential use, a new approved origin and path, and a response schema that needs fixture and live qualification before it can order accounts. The endpoint is proven in [`rate_limit_status_url`](https://github.com/openai/codex/blob/c0100ad4ecd2251c2b48b68534db08afac78c606/codex-rs/backend-client/src/client/rate_limit_resets.rs#L128-L133), and CLIProxyAPI supplies no implementation to port

If that read lands, new roots can rank by the bottleneck remaining percent across the windows for the requested limit family, with credits kept separate from included allowance. Existing pins and response references would stay put, as the [OLP code mode guide](../use/code-mode.md) already requires

The messages are proven in [Kimi Code error reference](https://www.kimi.com/code/docs/en/kimi-code/error-reference.html), and they still do not carry a reset timestamp, so the classifier can choose scope and label honestly while the deadline stays a conservative local fallback

Do not derive a reset from a subscription date that OLP does not know, and do not treat the Moonshot paid balance endpoint as a Kimi Code quota read. The plan split is documented in [Kimi Code membership benefits](https://www.kimi.com/code/docs/en/kimi-code/membership.html), while the balance endpoint belongs to [Kimi Open Platform balance](https://platform.kimi.ai/docs/api/balance)

Enrollment should also record whether Extra Usage is enabled for the member. With it enabled, the absence of a quota error can mean paid fallback spending rather than spare subscription allowance, so ordering and accounting should not describe that account as simply healthy subscription capacity. Source is [Kimi Code membership benefits](https://www.kimi.com/code/docs/en/kimi-code/membership.html)

### Qwen Token Plan

Port nothing from CLIProxyAPI, and do not port the separate Alibaba Coding Plan windows either. The Token Plan signal worth classifying is the documented `insufficient_quota` monthly exhaustion, kept apart from the short request rate limit. Source is [Alibaba Model Studio Token Plan Team FAQ](https://www.alibabacloud.com/help/en/model-studio/token-plan-team-faq)

New work would be that exact classifier plus an honest reset source. The vendor error does not carry the seat subscription anchor or the next reset instant, so OLP either needs operator supplied subscription cycle metadata or it keeps the current retry fallback and lets a later pinned request test recovery. Computing a reset from the calendar month alone would invent the anchor. Source is [Alibaba Model Studio Token Plan Team FAQ](https://www.alibabacloud.com/help/en/model-studio/token-plan-team-faq)

Static weights can already reflect seat size for new conversations from the documented monthly Credits per seat. There is no documented seat key remaining endpoint to rank live accounts, and owner console usage does not fill that gap. Source is [Alibaba Model Studio Token Plan Team FAQ](https://www.alibabacloud.com/help/en/model-studio/token-plan-team-faq)

### OpenCode Go

Port nothing from CLIProxyAPI, because it does not parse the Go allowance charge. The generic `Retry-After` behavior is already the shared floor. Source is [`openAICompatRetryAfter`](https://github.com/router-for-me/CLIProxyAPI/blob/585f97deac9aa57c700301221fb1a7085e1827cc/internal/runtime/executor/openai_compat_executor.go#L1351)

New work would observe `opencode.allowance` as an observed charge on the attempt, across the Chat, Messages, and Responses shapes that the adapter serves. That value can improve accounting and can support a clearly labelled least OLP observed spend tie break for new roots. It cannot prove remaining vendor allowance, because the response gives no remaining amount, no window anchor, and no reset time. Source is [OpenCode Inference API cost](https://opencode.ai/v2/docs/console/api/inference/#cost)

A stronger Go ordering would need operator supplied plan and billing anchor metadata plus a rule for work done outside OLP. Without that, a summed local estimate should stay out of admission, hard budgets, and any customer facing remaining quota claim. The documented windows explain why an account can stop, and they do not turn a local sum into a vendor balance. Source is [OpenCode Go](https://opencode.ai/docs/go/)

### Recovery boundary for every adapter

None of these signals widens replay by itself. A documented quota code proves why an upstream says it refused a request, while OLP recovery also needs a complete pre output rejection, portable input, settled earlier attempts, and the published recovery policy. Sources are the [OLP code mode guide](../use/code-mode.md) and [ADR 0002 on state aware code account recovery](../adr/0002-state-aware-code-account-recovery.md)

Extending [`InitialRejection`](../../internal/codeadapter/recovery.go#L18-L44) beyond Codex is therefore new adapter proof, not a CLIProxyAPI port. Each added envelope needs controlled fixtures for the exact HTTP shape and live qualification before it can move a conversation, and streamed or ambiguous failures stay on the original account with their usage uncertainty intact
