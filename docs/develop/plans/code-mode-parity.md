# Coding-client capability baseline and roadmap

This is the source-backed baseline for [#522](https://github.com/tyk-swe/olp/issues/522) and its documentation ticket [#523](https://github.com/tyk-swe/olp/issues/523). The goal is coding-client workflow parity with CLIProxyAPI and reliable governed pooling for teams. It is not a claim of parity with every competitor feature. The first new workflow is Claude Code using an enrolled ChatGPT subscription, including multi-turn tools, child agents, resume, cancellation and shared-account operation.

The comparison was checked on October 30, 2026 against CLIProxyAPI **v8.0.47**, commit **90c447d3a8727d115aa7552ec93ce023736ed492**, and OLP commit **fe594971b783c1a1ac9be7064fd9026ce7b396d1**. The competitor checkout and release tag resolve to that same commit. All source links below are pinned to these revisions. Later implementation work must update its own status and evidence without rewriting this historical baseline.

This investigation inspected source and existing qualification records. It did not run competitor code, fixture suites or real subscription workflows. OLP's existing [qualification record][O-qualification] reports controlled fixtures, not live subscription acceptance. Live qualification is outside the authorized implementation work and remains open. Neither this document nor a completed implementation ticket closes a live gate.

Later allowance, reset and hard-token evidence is recorded separately in the [allowance research report](code-mode-allowance-research.md). That report preserves unsupported guarantees and defines bounded follow-up qualification work.

## Reading the matrix

| Classification | Meaning |
| --- | --- |
| Implemented | Baseline source contains the stated behavior. The evidence column still limits any support claim. |
| Unqualified | Implementation or fixture evidence exists, but required real-client, platform or live-account evidence is missing. |
| Missing | The selected coding workflow requires implementation absent from the baseline. |
| Deferred | A coding-relevant capability is recorded for later work with an explicit dependency or decision gate. |
| Equivalent | Existing OLP architecture supplies the required outcome through a different interface. Its qualification limits still apply. |
| Excluded | Deliberately outside this coding-client parity claim. |

Implementation and qualification are separate dimensions. An implemented row can have fixture-only evidence, and an unqualified row does not imply that its code is absent. A source registration, model catalog entry, successful build or test file is not proof of a complete supported workflow. The completion criteria below describe the target, not current support.

## Delivery order

| Milestone | Dependencies and completion |
| --- | --- |
| M1, baseline and contracts | This matrix, the glossary and compatibility/recovery ADRs establish the contracts. Native paths needed by the first workflow require separate qualification. Track official-client drift through [#506](https://github.com/tyk-swe/olp/issues/506). |
| M2, Claude Code on ChatGPT | Depends on M1. Implement explicit translation, route-visible models, generated setup, complete supported tool exchanges and continuation, and initial safe shared-account behavior. Regression evidence and live qualification remain separate gates. |
| M3, governed pooling | Depends on M2 and the recovery contract. Demonstrate deliberate distribution, durable affinity, bounded safe recovery, reset handling, revocation and attributed uncertainty across accounts and replicas. Extend the client matrix. |
| M4, credentials and paid fallback | Depends on M1 authority and M3 recovery. Add Claude and Antigravity enrollment, validated one-time imports, identity-preserving lifecycle and explicitly authorized metered participation. Qualify each combination separately. |
| M5, remaining breadth and portability | Depends on the contracts introduced by M2–M4. Complete code-resource export/plan/apply and operator surfaces, then remaining ranked protocol, adapter, catalog, allowance and platform gaps. Proven hard-token support is separately gated. |

## Contract and evidence boundaries

The [glossary](../../../GLOSSARY.md) distinguishes adapters, coding plans and paid API targets. [ADR 0001](../../adr/0001-explicit-code-mode-compatibility.md) records the separate compatibility opt-ins and route-administrator authority. [ADR 0002](../../adr/0002-state-aware-code-account-recovery.md) records the execution and continuation evidence required for recovery. Existing published routes keep their contract until deliberately changed.

Each advertised combination needs deterministic regression evidence and an authorized live workflow. Record the integrated OLP revision, exact client package/version, operating system, adapter/profile, model, operation, protocol and transport, together with user-visible setup, commands and sanitized output. Console changes need the actual browser journey and screenshots when demonstrating behavior. An unrun, unavailable, pending or failing gate remains open. Current-client drift, fixture qualification and live qualification must remain separately visible.

For native paths, preserve unknown fields, body/response fidelity, stream ordering and credential isolation. For translated paths, exercise tool results, fragmented arguments, supported reasoning, child agents, resume and compaction. For recovery, observe actual execution counts under known rejection, ambiguous dispatch, partial output, cancellation and socket loss. For team operation, exercise multiple accounts/replicas, live revocation, durable affinity and usage uncertainty through the public gateway and management API. These are acceptance criteria, not claims that those tests or live workflows ran for this document.
