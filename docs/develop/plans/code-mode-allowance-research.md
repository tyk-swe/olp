# Coding allowance observations and hard-token evidence

This report answers [#555](https://github.com/tyk-swe/olp/issues/555), part of [#522](https://github.com/tyk-swe/olp/issues/522). It supplements the [pinned capability baseline](code-mode-parity.md) without changing that historical comparison. Sources were checked on October 30, 2026. OLP source was inspected at `7b27d0a6d21d3ea231671e9093b24d96d9bfde2b`. The competitor remains CLIProxyAPI v8.0.47 at `90c447d3a8727d115aa7552ec93ce023736ed492`.

Additional non-inference allowance observations are worth investigating. No source reviewed here establishes a conservative pre-dispatch bound over total reported tokens for an existing subscription adapter. Every subscription adapter in this report therefore remains unsupported for positive hard-token-budget guarantees. A successful request, finite live sample, client estimate or `count_tokens` response cannot supply that missing contract. This is a research result, not an implementation or qualification claim.

The user explicitly excluded live qualification from this run. This investigation read public documentation, pinned source and an existing official client artifact. It made no account requests, inference calls or synthetic health probes, and accessed no credentials. Live acceptance remains open.

## Keep the quantities separate

| Quantity | What the evidence can establish | What it cannot establish |
| --- | --- | --- |
| Request/token rate limit | Capacity over a named rate period, sometimes with a retry or replenishment time. OpenAI documents RPM/TPM and organization/project scope. Anthropic documents independent request, input and output rate headers. | A subscription balance, a monetary budget or a maximum total token debit for the next operation. [OpenAI rate limits][OA-rate] and [Anthropic rate limits][AN-rate]. |
| Monetary spend or credits | A provider-specific credit balance or metered cost under its own price and authorization rules. | A universal conversion into subscription requests or tokens. Codex credit prices do not determine included subscription use, and Antigravity overages can consume purchased credits. [Codex pricing][OA-plan] and [Antigravity plans][AG-plan]. |
| Observed usage | Authoritative consumption reported after an operation. Native usage may include invisible tokens and cache dimensions. | A pre-dispatch maximum, or zero consumption when a terminal counter is absent. [OpenAI token counting][OA-count] and [OLP settlement][O-settlement]. |
| Subscription allowance | A dated observation for an identified account, product, model or shared window. Percentages and reset times can inform eligibility. | An exclusive reservation against other clients, a token conversion or proof that the next operation will fit. Claude shares limits across product surfaces, while Codex and Antigravity vary consumption with the work done. [Claude usage limits][AN-plan], [Codex pricing][OA-plan] and [Antigravity plans][AG-plan]. |
| Hard total-token bound | A provider-enforced, versioned upper bound on the exact operation's total reported consumption, known before dispatch and supplied by a qualified adapter. | An operator constant, local tokenizer result, context size, output-only cap, observed allowance or sampled maximum. [OLP bound contract][O-contract] and [existing qualification analysis](../qualification.md#native-hard-token-bound-research). |

## What OLP implements today

The [adapter registry][O-adapters] covers Codex, Claude, Antigravity, OpenCode Go, GLM Coding Plan, MiniMax M Plan, Kimi Code and Qwen Token Plan. Codex alone selects the allowance parser. Other families select usage observation. Claude serves native Messages. Antigravity requires the explicit Chat translation policy and a cloudcode generation envelope, with live subscription and client qualification still open. Enrollment and identity verification do not qualify allowance or generation.

[Codex observations][O-codex] retain primary and secondary windows per metered feature and separate credits. [Allowance merging][O-observations] retains observation times independently for windows, token counts, request counts and credits. Older dimensions cannot replace newer ones. Missing fields do not clear unrelated dimensions. A newer observation without a reset retains an earlier reset only while that reset is still in its future. [Eligibility][O-availability] permits another attempt after a supported exhausted window's reset, subject to every other gate. It does not write a replenished balance. Unknown resets keep exhausted dimensions blocked.

These timestamps order observations, but are not a provider freshness guarantee or a universal cache lifetime. An external client can consume allowance after a read. Polling must not reserve that capacity locally or turn an old positive observation into an entitlement promise. Health cooldowns and `Retry-After` remain independent of allowance observations, and a successful identity refresh must not clear a newer quota cooldown. See the [current user contract](../../use/code-mode.md#limits-and-accounting).

The current schema has named percentage windows, account-level token/request observations and one credit balance. It does not attach a currency or provider-defined credit unit to that balance, or a model/workspace scope to the account-level counts. A new reader needs an explicit, lossless semantic mapping before reusing those fields. Endpoint discovery alone cannot justify collapsing separate scopes or converting plan credits into tokens or money. See the [observation types][O-observations].

## Identity, privacy and refresh boundaries

Each observation must belong to the same enrolled principal and credential generation that authorized its read. Codex carries the selected ChatGPT account. Claude enrollment verifies account and organization, and refresh rejects changes to those facts. Antigravity enrollment verifies the authenticated Google subject and existing cloudcode project, and refresh rejects either changing. Pasted keys use a profile-specific fingerprint, not a verified human or organization identity. Rotation to a different key cannot silently inherit the old principal or its observations. These are [existing credential][O-credentials] and [grant][O-claude-auth] [contracts][O-ag-auth], not claims inferred from unverified local token data.

A future reader should refresh through the existing grant lifecycle, then recheck current account authority and identity. A late response from a replaced, revoked or changed principal must not update the replacement account. Transport failures, 401/403, rate limiting and an explicitly exhausted allowance need distinct outcomes. Failed or partial reads must not invent a reset, erase independent exhaustion or trigger synthetic generation. An unknown observation remains unknown. This is a proposed acceptance boundary, not a claim that a background reader already exists.

Non-inference does not mean content-free. Token counting sends the supplied prompt, tools and possibly files or images to a provider. Quota reads can expose account identifiers, plan information, spend and balances. A reader should persist only validated, bounded numeric/window metadata and observation provenance, and exclude raw responses, headers, credentials, prompts, outputs and tool content from OLP diagnostics. Existing OLP diagnostics are described [here](../../use/code-mode.md#fidelity-and-privacy).

Provider retention depends on the exact product, endpoint, account terms and settings. [OpenAI API data controls][OA-data] describe the API surface and do not establish retention for ChatGPT's private usage endpoint. [Claude Code data usage][AN-data] distinguishes consumer preferences from commercial terms and separately describes local transcript storage. Eligibility for zero data retention on an API token-count endpoint is not evidence that a consumer OAuth account has that configuration. No endpoint-specific retention promise was established for the private quota reads in this report.

For key plans, [OpenCode Go][OC-plan] delegates relevant training/retention choices to workspace settings and model policy. [Qwen Team Edition][QW-plan] excludes conversation training, which does not establish a retention period or quota-metadata policy. No endpoint-specific retention contract was established for these five families.

[Antigravity terms][AG-terms], checked on the research date, distinguish administrator-governed enterprise/API-key use from the consumer terms. The latter describe storing interaction metadata, possible human access and continued service/safety use when telemetry is disabled. They explicitly restrict third-party tools accessing Antigravity OAuth and describe possible suspension. This is a dated provider restriction and account-risk fact. It does not prove protocol failure or replace technical qualification. It does not create a new approval gate for this research or authorize endpoint traffic.

## Why output limits and counts do not yet prove a hard bound

For a single accepted dispatch, the required inequality is `reported_total_tokens <= reserved_bound`. Its proof must cover the exact adapter, origin, model version, operation and transport. It must include all reported input, generated output, hidden/reasoning work, cache reads and writes, retained context, server tools, retrieval and any internal iteration or compaction included in that total. Input-cache counters and reasoning counters must follow the provider's accounting rules rather than being added twice. A model's context window only describes resident context unless the provider separately bounds cumulative work.

| --- | --- | --- |

The [public Responses API reference][OA-output] defines an output bound including reasoning. The [public token-count endpoint][OA-count] describes exact input counting for its API surface. | Struct field absence does not exclude extra-field dispatch or establish that every backend rejects or ignores an extra field. It supplies no guarantee that a supplied cap is enforced on ChatGPT subscription operations. No source connects the public API count/cap contract to subscription dispatch, opaque continuation, compact or total internal work. Unsupported. |
| Claude subscription Messages | The [Messages API][AN-message] documents `max_tokens` as a generated-token ceiling. No bound implementation or budget-policy change follows from this report. [Admission][O-admission] requires adapter evidence only when a matching hard budget applies. [Settlement][O-settlement] preserves unknown consumption and blocks future budgeted work after a bound violation. Request/rate/concurrency controls and supported allowance checks can remain useful without pretending to offer a hard-token guarantee.

## Bounded follow-up specifications

**F1, Codex read-only allowance refresh.** Implement only the applicable authenticated usage read using the existing account authority and refresh lifecycle. Allowlist the origin/path and supported metadata. Exclude credit-reset and paid actions. Through the public management API and a subsequent gateway request, regress independent primary/additional windows, stale and partial reads, malformed resets, credential replacement, revocation and an exhausted dimension whose reset is missing. Assert observed eligibility and actual upstream request counts, including zero generation calls during maintenance. Authorized live evidence must show a current official client's `/status` or usage view agreeing with the same account's sanitized read at a recorded time, without fixing external allowance numbers in tests.

**F2, Claude subscription allowance qualification and ingestion.** First pin the current official usage transport and document account/organization ownership, field units, window identities, reset encoding and separation of overage spend. Then add only proven usage dimensions through the shared observation path. Public management/gateway regressions must show that API RPM/TPM headers do not become subscription tokens, independent weekly/session exhaustion survives partial and stale reads, and a mismatched/refreshed principal cannot update the prior account. Maintenance must make no inference calls. Authorized live evidence must compare the same account's official usage view with the sanitized read/passive signal before and after a genuine user workflow. The existing live gap remains open until that evidence exists.

**F3, Antigravity quota endpoint applicability.** Establish the authorized account/project and exact daily-cloudcode method, origin, request envelope and response schema for non-inference discovery. Keep model groups, percentages, counts, weekly windows and purchased credits distinct. Do not infer them from public Gemini rate limits. Only then implement supported observations. Public management/gateway regressions must cover independent model-group exhaustion, missing/invalid reset, project/principal mismatch, stale credential completion, partial catalog data and zero generation/onboarding requests. Authorized live evidence must correlate the official `/usage` view and sanitized same-principal/project data, recording product/account terms separately from protocol results.

**F4, adapter-qualified total-token proof.** Select one exact provider/model/operation and bounded request feature set only after a provider-owned contract establishes all input and generated-work limits and their accounting scope. Record the source version and a bound derivation. If evidence remains absent, deliver a documented unsupported result rather than an estimate adapter. Any eventual implementation must fail before dispatch for unsupported content, hidden state, transport or model versions. Public gateway regressions must exercise the admitted maximum, all overlapping budgets, concurrent reservations, cache/reasoning accounting, missing terminal usage, cancellation and a controlled bound overrun that blocks subsequent budgeted admission. Live evidence can corroborate an established contract but cannot prove a universal upper bound from finite samples. No synthetic qualification or weaker limit is an acceptable substitute.

**F5, key-plan allowance qualification.** Scope each change to one exact profile, credential kind and source-owned read endpoint. GLM needs current regional unit/reset semantics. MiniMax needs exact host and subscription-key applicability. OpenCode needs verified workspace association. Kimi needs current pasted-key permission evidence. Qwen first needs an official member-applicable quota API contract. Record principal scope, field direction/scale, independent windows, timestamp or duration units, missing data and spend fallback. Define the mapping into OLP's observation schema without erasing scopes or units. Public management/gateway regressions must show independent exhaustion, stale/partial/malformed data, wrong workspace/key/profile rejection, separate paid credit and rate capacity, and zero inference during maintenance. Authorized live evidence must compare the same account/key/workspace's official usage view with sanitized read data at a recorded time, including an observed reset or genuine user-workflow change. Do not pin external balance values or enable unqualified profiles.

## Evidence limits and validation

The current official Codex source revision was resolved through the first-party repository on the research date. The Claude artifact was already downloaded for enrollment research and was read without installation or execution. Its endpoint strings and reader show first-party client behavior, not a public stability guarantee. The earlier auth evidence from #541, #542 and #544 was reused for scope and identity, with new external claims checked against current primary sources.

The key-plan investigation used a separate bounded researcher and current first-party source/documentation. An attempted Z.ai plan-usage page was inaccessible, and some MiniMax landing pages yielded no readable content. The report uses readable official FAQs and pinned clients rather than treating those retrieval failures as evidence about service behavior.

Public source/document retrieval and local link/diff checks are the only validation for this change. Some direct Markdown fetches from Claude returned HTTP 403, while the connected web reader opened their official HTML pages. The general Responses reference exceeded the web reader's size limit, so the official Python reference and downloadable Markdown were used. These retrieval limitations are not account authorization results. No live account endpoint, counter-reset transition, real-client journey, retention configuration or positive token-bound contract was qualified. Application tests would not prove these documentation claims and were not run.
