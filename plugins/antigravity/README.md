# Antigravity enrollment and controlled code mode

This plugin enrolls an existing Antigravity account through headless Google OAuth. Enrollment does not prove subscription entitlement, live inference, allowance, account health or a working live OpenCode tool session. No current model has been qualified by this change.

The operator must supply an authorized Google desktop OAuth client and configure its public `client_id` provider option. Create the provider from the `antigravity-subscription` profile, start its normal grant enrollment and open the returned URL in a browser. The flow uses PKCE S256 and offline authorization. OLP does not run a local callback listener. After consent, copy the loopback callback URL even if the browser reports a connection error.

Complete enrollment through the existing masked grant input with JSON containing `callback_url` and `client_secret`. The secret comes from the operator's Google OAuth client configuration. Do not put it in provider options, URLs, logs or shared configuration. For example, replace both placeholders in `{"callback_url":"http://127.0.0.1:51121/oauth-callback?code=...&state=...","client_secret":"..."}`. OLP stores the client secret and refresh token together in the existing encrypted refresh grant. The PKCE session also uses existing encrypted enrollment storage.

OLP gets the stable subject from authenticated Google OpenID userinfo and verifies an existing cloudcode project through `loadCodeAssist`. Email and unverified local token claims never establish the principal. Enrollment refuses accounts without that project and does not call onboarding or inference. Refresh verifies the subject and project again and rejects any change while retaining the original account identity.

The controlled target requires the route administrator to enable `chat_to_antigravity` and publish the route. Generated OpenCode configuration uses the existing Chat Completions ingress with `@ai-sdk/openai-compatible`. The internal target wraps canonical Gemini requests in the cloudcode project/model/request envelope. Only explicitly configured `gemini-` model IDs are eligible for this target. This family check is a routing restriction, not a current model inventory or live acceptance claim.

The supported controlled combination is OpenCode Chat Completions, one candidate, text and function tools, over HTTP unary or SSE. Request aliases require the independent existing model rewriting policy. Responses, Messages, WebSocket, public Gemini ingress, images, audio, server tools, reasoning controls and signed thought state are unsupported. Native accounts retain native request and response bytes, and client identity and prompt compatibility stay disabled. The gateway settles observed Gemini terminal usage independently of whether the client requested usage disclosure. Cancellation stops upstream work, and a partial response has unknown usage unless authoritative terminal counters were observed.

Google's current Thinking guide says generateContent thought signatures can attach to any part, including function calls and final response parts, and must be retained for reasoning continuity. The current canonical projection cannot carry that state faithfully through Chat history. This target rejects signed or thought parts with `code_upstream_unsupported_state` rather than returning tools with missing state. Any authoritative terminal usage already observed still settles through the existing ledger, and the request is not replayed. Incoming unrepresentable state is refused before dispatch. A current model and live tool workflow that can complete this restricted path, or faithful signature support, remains a concrete qualification prerequisite. Unsigned fixture tool success does not satisfy it.

Authentication follows the [Google native OAuth guide](https://developers.google.com/identity/protocols/oauth2/native-app), [OpenID discovery](https://accounts.google.com/.well-known/openid-configuration), [OpenID Connect guide](https://developers.google.com/identity/openid-connect/openid-connect) and [Thinking guide](https://ai.google.dev/gemini-api/docs/thinking), checked on 2026-10-30. The private cloudcode envelope and project lookup are source-observed behavior in CLIProxyAPI commit `90c447d3a8727d115aa7552ec93ce023736ed492`, specifically `internal/auth/antigravity/auth.go` and `internal/runtime/executor/antigravity_executor.go`. This plugin does not copy that project's client secret, inject client identity or prompts, rewrite reasoning signatures, or probe inference.

## One-time credential import

The management import accepts a narrow Antigravity migration JSON envelope. It does not extract arbitrary IDE authentication stores. The envelope requires `type` equal to `antigravity`, `access_token`, `refresh_token`, `client_id` and `client_secret`. The latter two must be the original OAuth client authorization that issued the refresh token. The client ID must also match this provider's public `client_id` option. A raw token export without the original client authorization cannot be refreshed. Re-enroll with an operator-authorized OAuth client when that authorization is unavailable. Never substitute another client's credentials.

The supported field names follow the flat token export in the pinned CLIProxyAPI `sdk/auth/antigravity.go`, commit `90c447d3a8727d115aa7552ec93ce023736ed492`, inspected on 2026-10-30. That export omits client authorization, so the unmodified file alone is insufficient. No vendor client secret is included in OLP. Optional export metadata includes `expired` as RFC3339, positive integer `expires_in` and `timestamp`, string `email`, and string `project_id`. A supplied expiry must be in the future and no more than ten years away. A supplied project must match the authenticated project. Email and local timestamps do not establish identity. Other fields, duplicate JSON members, service account credentials and raw IDE stores are rejected.

Import through the provider's masked console import field or `POST /api/v1/providers/{provider_id}/antigravity-import`, supplying the current `If-Match` and a JSON body with `credentials` containing the envelope as JSON text. An optional `slot_id` selects an existing slot. This uses the same configure authorization and CSRF requirements as enrollment.

OLP authenticates the original access token against fixed Google userinfo and Cloud Code Assist project endpoints. It then refreshes through the trusted subscription plugin using the original client authorization and requires the same verified subject and project. Unverified local claims cannot establish either identity. An occupied slot must retain its principal. Import uses the shared encrypted grant storage, checks the provider revision again before staging, and returns no credential material. OLP owns refresh after import. Stop using the old local credentials to avoid competing refreshes. Import does not synchronize files, probe inference, or add signed-state compatibility.
